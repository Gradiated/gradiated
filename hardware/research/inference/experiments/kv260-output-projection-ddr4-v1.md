# Experiment 14 · Fetch attention output weights from DDR4

Selected on 18 November 2026. Preparation is under way. The control is [attention-exp-pair-v2](../implementations/kv260/README.md#selected-circuit-comparison-baseline). Keep the frozen W16A16 model, prompts, 50 MHz clock, paired exponential units, multiply order, rounding and remaining storage fixed.

## Question and intervention

How long does the arithmetic wait if it requests each weight from the module’s DDR4 as it needs it? The selected matrix combines the two attention heads’ outputs. It is bank 4 of the loader, with 32 output rows of 32 signed 16-bit weights. The control reads a weight from BRAM during its READ step and multiplies on the next step. In [Experiment 12](kv260-output-projection-lutram-v1.md) that schedule remained identical when the same array moved to LUTRAM.

For the first DDR4 comparison use one outstanding read and one aligned 64-bit AXI beat for each requested weight. Select its signed 16-bit lane using the low address bits. Consume that weight, then discard the other lanes. Request the next weight when its turn arrives. A full pass consumes 2,048 useful bytes through 1,024 reads carrying 8,192 bytes at this 64-bit interface. This deliberately measures the cost of individual requests. Fetching a row in a burst and reusing all the returned weights would answer a different question. Confirm the selected port and routed width first. Record a protocol revision if that interface cannot be implemented as specified.

Use the same qualified, routed circuit for both timed arms where possible, switching between BRAM and DDR4 while idle. This matches the memory interface, clock setup, counters and placement. Pin the mode for each run. Verify that BRAM mode matches the adopted circuit’s outputs and original FPGA cycles. In DDR4 mode disconnect the BRAM weight response from the arithmetic and prove the external input is used with a controlled matrix perturbation in simulation. Both storage paths will occupy the comparison image. Its resource report measures the fixture cost. A DDR4-only route would be needed to claim area freed by removing the BRAM.

The same digest was obtained independently from tensor O in the frozen fixed-point model.

The existing PS-to-FPGA AXI-Lite path carries host commands. A separate read-only FPGA master must reach DDR through a verified PS slave port. Verify port width, clock, reset, address aperture and AFI settings against the implemented design. Inventory the running kernel’s device drivers, DMA allocation and address translation before choosing the host buffer path. A Linux allocation must be pinned and mapped for this device. Verify its **device-visible** base and length, cache visibility after the CPU writes, and ownership until the last read is drained. The last aligned beat must lie entirely within the allocated range. The historical CMA reservation establishes capacity only. A user-space pointer or assumed physical address is insufficient. If a new kernel driver or boot configuration is necessary, document that dependency before changing the board.

## Board inventory on 18 November 2026

Read-only checks over USB serial confirmed Ubuntu kernel `6.8.0-1015-xilinx` and the stock `k26-starter-kits_image_1` overlay on this boot. All four UIO devices were AXI performance monitors. The `reserved` and `system` DMA heaps existed and were root-only. Linux reported 800 MiB of contiguous-memory capacity. The kernel also exposed `/dev/udmabuf`. These observations establish that the kernel offers buffer allocation. They do not establish a DMA address for our accelerator.

The installed kernel includes `uio_dmem_genirq.ko.zst` and matching kernel headers. Before selecting a driver, check which device owns the DMA mapping, how the accelerator receives the bus address, how the CPU makes the written weights visible, and what holds the allocation until the FPGA finishes. Verify the chosen path on this boot before collecting inference measurements. The inventory did not allocate a buffer, bind a driver or reprogram the FPGA.

## Evidence and measurement

1. Run the dense fixture with independently decoded weights. Check all 1,024 accepted operand values and addresses, signed products, sums, rounding, row outputs and saturation. Inject backpressure on the AXI address and response channels, faults, incorrect response completion and reset with a read outstanding. Prove bounded termination, drain or isolation before buffer release, and recovery. Run the seven frozen RTL cases against reference logits, generated bytes, stop reasons and cache state. Compare checkpoints at equal model steps even though DDR response clocks can vary.
2. Count by request and projection invocation. Record useful weight bytes, accepted AXI reads, accepted return beats and response errors. Count additional blocked FPGA clocks between the ordinary weight-capture edge and the edge on which a usable weight reaches the arithmetic. Separate address backpressure from response wait. Exclude setup and cycles already required by the BRAM schedule. Reconcile stage and total clocks on the same inference work. Returned AXI bytes describe the measured interface. Physical DRAM traffic requires a controller measurement.
3. Use Vivado 2025.2, two jobs and the 20 ns clock constraint. Verify the actual read path, address limits, logic selecting the operand, memory census and timing closure. Allow 45 minutes for the first route plus five minutes for artifact recovery. Run the initial RTL suite with two jobs and a 25-minute limit. Preserve failures and report any budget revision.
4. Qualify both modes on the physical board before timing. Verify byte-identical replies and counts. DDR response latency varies on hardware, so validate causal order and transaction counts independently from measured elapsed cycles. Do not require board waits to equal a simulated delay. Compare a matching ready-but-idle interval in each mode. Load and verify weights before the timed window, and report that setup separately. Check clocks, reset, peripheral state and background activity before and after each block.
5. Use the [standard scorecard](measurement-standard-v2.md) and the historical AB/BA/AB workload, 18 warm-ups and 36 timed replies across three prompts. Record TTFT, decode tokens/s, complete-reply time, internal cycles, module watts, J/answer, J/output token, tokens/J, paired variation and resource counts. Keep gross module readings and SPI1/TPM brackets for all six blocks. Set the physical watchdog from measured smoke timing before starting the fixed series. Stop on incorrect outputs, out-of-bounds reads, bus faults, hung progression, unverified clock state or inability to restore. Recover the packet and raw evidence to the Mac. Restore the agreed original research image and weights, verify all 320 original BOS scores and recheck the board state.

A slower result can answer the question. Compare extra projection wait cycles with extra whole-request cycles, then assess whether they explain the measured time and energy. Keep a possible burst or row-buffer follow-up separate from this experiment.

### Per-prompt energy extension

Before dispatch on 18 November, we added `ddr4-per-prompt-v1` to meet the three-prompt energy requirement. Keep the six mixed blocks above unchanged. In a separate series on the same image and boot, take two matched BRAM/DDR4 pairs for each prompt. Reverse prompt order on the second pass and alternate which mode runs first. Each homogeneous block has one warm-up of that prompt, followed by 18 timed replies for Hello, 12 for the six-byte input or eight for the 48-byte input. These previously observed reply durations put each control block around two seconds, long enough to sample power many times at 20 Hz. The weights remain resident and the context is cleared between replies.

Use the same output checks, clock, SPI brackets, idle windows and gross VCC_SOM integration as in the mixed blocks. Save the prompt ID and each block's duration, completed replies, output bytes and joules. Calculate J/answer and J/output token from those totals. Report the two pairs separately where their variation matters. Each energy estimate describes a block of repeated replies.
