# Longer repeatability on the KV260

**Status.** Workload, segment analysis and the longer sampling schedule prepared. Execution requires separate authorisation and integration review.

Use the same selected `scalar-div-v1` at 50 MHz, frozen `chip-joke-text-20261109` W16A16 model, greedy output, resident host and original exact three-prompt workload in the [manifest](../workloads/kv260-repeatability-v1.json). Earlier work had blocks of about a minute within one boot. Here we want to distinguish drift while the board stays busy from variation when starting fresh. Ambient temperature, clock settings, host scheduling, logger overhead and boot state can all influence the result.

## Within-session and cross-boot observations

Plan three independently qualified boots on the same board, one 10-minute contiguous verified workload per boot. Use one active request and context, with no queue. Begin each session with two verified warm-ups per case. Repeat the rotating three-case order followed by its reverse. Each six-request cycle includes every case twice. Admit requests until 600 seconds after the session start. Allow the last admitted request to finish within its 3-second absolute deadline, keeping it in a separate drain receipt if it completes outside the fixed windows. The request cap is 3,600 per boot. Reaching it before 600 seconds stops the workload and counts as an incomplete session, with recovered evidence.

Collect complete per-request output byte timestamps, done, verification, elapsed service, stop and context receipts. Report completed requests and output tokens by ten fixed one-minute segments, assigned by verified completion, and report drain separately. Show both total counts and per-case service and decode summaries, early and late segments, and the median and range across independently qualified sessions. Treat changes greater than 5% between the first and last two-minute windows as a descriptive drift flag. Keep unfinished or failed samples and their observation duration. Do not pool boots before examining them separately.

Pin each boot ID, board identity, firmware, host, available clock/CPU policy, initial conditions, ambient observations and cooling intervals. Use a fixed minimum 10-minute idle interval on the board between timed runs and record how long elapsed. If a separate authorised boot cannot be qualified, report the sessions actually observed. No automatic reboot. Boot-to-boot repetition on one device does not establish device-to-device reliability.

## Power, environment and safety

Prepare a continuous 610-second envelope at 20 Hz, 12,200 scheduled slots, including room for the two 2-second idle windows, 0.5-second guards and final drain. Use the existing qualified INA260 VCC_SOM sensor settings and unprivileged reader only. The injected collector retains slot start/end, missed slots and any partial error. The prepared variable-length validator checks every slot and integrates bracketed active and matched idle intervals using the existing trapezoid and five-alignment method, with a 75 ms maximum gap. Before execution, review the supervisor binding for reader identity, privilege and unchanged sensor state, sampling bounds and evidence export. Budget sample storage and export before dispatch. The existing 350-slot validator alone cannot admit this run. Missing power coverage leaves that metric unavailable.

Capture a fixed clock/sensor and memory snapshot before and after the active window, plus segment-boundary readings only where a read-only, qualified side sampler can provide them without changing timing. Record actual temperature channel availability, process RSS/lifetime high-water mark and system available RAM as distinct host measures. Unavailable telemetry limits thermal or memory claims. Review sensor overhead and scaling separately from whole-board energy or calibration. A timing-only version needs explicit admission and a separate scope.

Use a 12-minute active/telemetry watchdog per session with 3 seconds per service, five additional minutes for setup and restoration, and a separate bounded export stage with an evidence-size cap in the execution packet. Stop on the first unexpected board, correctness, evidence or deadline failure. Preserve all partial receipts and independently verify restoration of the original circuit and pinned weights when healthy. Follow [measurement standard v2](measurement-standard-v2.md) and the [handoff](kv260-milestone-preparation.md).
