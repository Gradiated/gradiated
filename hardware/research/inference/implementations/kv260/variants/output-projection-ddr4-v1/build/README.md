# KV260 Experiment 14 build

The fixture uses Vivado 2025.2 and two threads on the established Linux build host. The existing PS-to-PL AXI-Lite controls use HPM0 and base address `0xa0000000`. The projection read master connects directly to `S_AXI_HP0_FPD` with 49 address bits, 64 data bits and 6 ID bits. The block design assigns only DDR-low `0x00000000–0x7fffffff`. Both interfaces use PL0, constrained to 20 ns. The model still has the original BRAM projection storage for the control arm.

1. Materialise the experiment RTL with [materialise_projection_ddr.py](../materialise_projection_ddr.py) and pass its exact output directory to `prepare.py`. The input archive is the adopted pair-v2 `build-input.tar.gz`. The script verifies its SHA-256, each manifest entry, the baseline shell bytes and the candidate RTL manifest.
2. Archive the prepared directory contents. Extract them into the manifest's fresh `remote_root` on the established build host. Invoke `KV_OUTER_BUILD_UTC=$(( $(date +%s) + 2520 )) python3 -u run-all.py` from that directory. The 42-minute phase ceiling leaves up to three minutes for the remote archive, then five minutes for recovery.
3. Recover the archive and receipt and run `verify.py <archive> <receipt> <new-destination> <adopted-server.tar.gz> <acceptance.json> --manifest-pin <prepared-source-manifest-sha256>`. Verification checks the archive and per-file hashes, the seven logged phases, the direct HP0 address aperture, routed pins and width, the original BRAM path, timing, the generated PS register differences, the converted firmware payload and numeric device-tree properties.

The generated PS init adds two writes on HP0. These set the low two bits of `0xfd380000` and `0xfd380014` to 1 for the 64-bit interface. The candidate interface overlay encodes the same fields as AFI IDs 4 and 5 and preserves HPM0/1 setting ID 14. Its UIO and DMA platform resources have disjoint byte ranges. Generic UIO maps the full containing page, so the harness leaves DDR configuration writes to the DMA driver. [AMD 2025.2 device-tree generator](https://github.com/Xilinx/system-device-tree-xlnx/blob/xlnx_rel_v2025.2/device_tree/data/device_tree.tcl) · [TF-A register mapping and masked AFI writes](https://github.com/ARM-software/arm-trusted-firmware/blob/v2.8/plat/xilinx/zynqmp/pm_service/pm_api_ioctl.c)

The deployment companion is `kv260-ddr4-dma-direct.dts` compiled with the same DTC (`dtc -@ -I dts -O dtb`). Its additional `gradiated,verified-direct-dma` property admits the verified direct mapping in the driver. The direct-DMA companion overlay matches the experiment boot's empty `/axi/ranges`, absence of `dma-ranges`, and nonsecure SMMU `sCR0.CLIENTPD=1` from a nonsecure load at offset zero. The optional secure alias at offset `0x400` is a different access path. The candidate read address channel uses ID 0, nonsecure unprivileged data, and single 8-byte beats. [Arm SMMU v2 architecture](https://documentation-service.arm.com/static/5f900d34f86e16515cdc08fb)

On the admitted boot, record `timeout 5s python3 readback.py baseline > before.json` before programming. Use `timeout 5s python3 readback.py candidate --baseline before.json` after applying the candidate interface. The width fields may persist after overlay removal. Once all requests drain and the original image and interfaces return, the AFI restore overlay restores the captured width-zero fields without a fabric reset. Verify `timeout 5s python3 readback.py restored --baseline before.json` after removing the restoration overlay. The helper checks exact AFI words, FPD reset and the nonsecure SMMU bank against the initial snapshot.
