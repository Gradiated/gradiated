## Call your endpoint and log outcomes

`run.deploy()` (and `grad deploy`) sets up your endpoint using the artifact's defaults. Call the endpoint from your app and send back how well each response worked so live traffic improves the next run:

<DocsCodeTabs>
  <DocsCodeTab label="Python">

```python
router = client.endpoints.get("support-router")
decision = router.route(messages=messages, tools=tools)
reply = call_your_llm(decision.model, messages, tools)

decision.record_feedback(
    score=1.0 if user_resolved else 0.0,
    metrics={"cost_usd": reply.cost_usd, "latency_ms": reply.latency_ms},
)
```

  </DocsCodeTab>
  <DocsCodeTab label="TypeScript">


## Two ways to train

Start with a built-in `Recipe` and sensible defaults. When you need more control, override a single piece (like the loss function or dataset split), or write your own Python loop directly on `Trainer`.

| Mode | How it works | When to use it |
| --- | --- | --- |
| [**Recipes**](/docs/training/recipes/) | Pick a recipe (`RouterRecipe`, `DecisionModelRecipe`, `SFTRecipe`, `DPORecipe`, `GRPORecipe`, `DistillRecipe`, `CartridgeRecipe`, `RewardModelRecipe`, `EmbeddingRecipe`), chain stages with `.then(...)`, or run from YAML. | Almost always. You get sensible defaults, held-out evaluations, and can swap individual pieces without writing a training loop. |
| [**Custom loops**](/docs/training/custom-loops/) | Call `Trainer`, `Artifact`, `Environment`, and `Rubric` directly in Python with built-in losses or your own PyTorch `CustomLoss`. | You want a custom research loop, multi-trainer setup, replay buffer, or custom rollout logic. |

You can export the full resolved config of any run as YAML (`grad runs inspect <run_id> --yaml > recipe.yaml`) to check it into Git.

<DocsCallout label="Pay only for tokens trained" tone="tip">
You pay per million tokens processed (training and sampling) plus storage for saved artifacts and checkpoints. You never pay for idle GPUs. Start with the simplest option that proves value: a router or decision model trains quickly, then move up to fine-tuning or RL once you have a baseline.
</DocsCallout>

## Using with coding agents

Every docs page includes a **Copy** menu (**Copy page** as raw Markdown or **Copy prompt** for coding agents) in the top right, and every page is served as plain Markdown at `<url>.md`, indexed in [`/llms.txt`](/llms.txt) and `/llms-full.txt`.

The CLI is designed for non-interactive agent loops: pass `--json` to any `grad` command for a single JSON envelope on stdout, and run `--dry-run --json` (or `client.runs.plan(...)`) to validate dataset coverage and estimate tokens and cost before starting a run.

### Starter prompts to paste into Claude Code, Codex, or Cursor

<DocsCodeTabs>
  <DocsCodeTab label="Model router">

```text
Read https://gradiated.com/docs/training/recipes/router.md and integrate a Gradiated model router into this codebase:
1. Find where we call LLMs and inspect how we log or store completed requests and outcomes.
2. Push or import historical traces into a Gradiated dataset using GRADIATED_API_KEY from env.
3. Run `grad train --dataset <name> --name <router> --recipe router --dry-run --json` first and fix any data warnings.
4. Train the router, verify `eval_report.pareto_summary.quality_drop_ci95` stays inside 2%, and deploy with `grad deploy <router>@latest --canary 0.10`.
5. Wire `client.endpoints.get("<router>").route(...)` and `client.feedback.record(...)` with idempotency keys.
```

  </DocsCodeTab>
  <DocsCodeTab label="Fine-tune (SFT & DPO)">

```text
Read https://gradiated.com/docs/training/recipes/sft.md (and https://gradiated.com/docs/training/recipes/dpo.md) and set up a fine-tuning pipeline for our task:
1. Export verified passing examples into a Gradiated `Dataset` (`input.messages`, `expected_output`, `session_id`, and `scores`).
2. Score the dataset with a `Judge` (`dataset.score(judge).wait()`) and filter to high-scoring examples (`dataset.filter(lambda t: t.scores["clean"] >= 0.8)`), then configure an `SFTRecipe` (chaining into `DPORecipe` with `.then(...)` if needed) with `Model(...)` and `splits.BySession()`.
3. Validate with `client.runs.plan(...)` or `grad train -f recipe.yaml --dry-run --json` before starting training.
4. Deploy with `strategies.SyntaxFallback(fallback=Model(...))` and wire `feedback.record()` so human fixes are captured as `expected_output`.
```

  </DocsCodeTab>
  <DocsCodeTab label="RL agent (Docker Compose)">

```text
Read https://gradiated.com/docs/training/environments.md and https://gradiated.com/docs/training/recipes/rl-agents.md:
1. Subclass `grad.Environment` around our existing `docker-compose.yml` and seed script (`setup`, `step` returning `Observation(text=...)`, `evaluate` before `teardown`, and guaranteed `teardown`).
2. Write a `Rubric` with deterministic `StatefulScorer` assertions against the live container state.
3. Run a 2-task smoke test against a base `Model` (`client.models.get(...)`, `max_concurrency=2`) to verify `loss_mask` masks tool outputs and containers clean up cleanly.
4. Wire a GRPO / async CISPO loop using `with client.trainers.create(model=Model(...), adapter=adapters.LoRA(rank=32)) as trainer:`.
```

  </DocsCodeTab>
  <DocsCodeTab label="Distill / Cartridge">

```text
Read https://gradiated.com/docs/training/recipes/distillation.md (or https://gradiated.com/docs/training/recipes/cartridges.md):
1. Identify our high-volume frontier prompts or repeated long system prompts.
2. Configure `DistillRecipe` (32B teacher -> 4B/8B student) or `CartridgeRecipe` (`adapters.PrefixKV` over our static context).
3. Validate with `client.runs.plan(...)` or `grad train -f recipe.yaml --dry-run --json`, run training, compare `eval_report` against the baseline, and deploy with `--shadow` first.
```
