# Training overview

<DocsLead>Train routers, decision models, and fine-tuned models from your production logs or test environments.</DocsLead>

<DocsCodeTabs action={<DocsApiKeyAction />}>
  <DocsCodeTab label="Fine-tune a model (60s)">

```python
from grad import Grad
from grad.recipes import SFTRecipe

client = Grad()  # reads GRADIATED_API_KEY

# Plain chat records (the OpenAI fine-tuning format). The last assistant turn is what the model learns.
dataset = client.datasets.push("sql-quickstart", [
    {"messages": [
        {"role": "user", "content": "Count active users from yesterday."},
        {"role": "assistant", "content": "SELECT count(*) FROM users WHERE active_at >= current_date - 1;"},
    ]},
    {"messages": [
        {"role": "user", "content": "Total revenue by plan this month."},
        {"role": "assistant", "content": "SELECT plan, sum(amount_usd) FROM invoices WHERE created_at >= date_trunc('month', current_date) GROUP BY plan;"},
    ]},
])

recipe = SFTRecipe(model="qwen/qwen3-8b")

# $0 preview: resolved defaults, warnings, tokens and cost
print(client.runs.plan(dataset=dataset, name="sql-helper", recipe=recipe))

run = client.runs.create(dataset=dataset, name="sql-helper", recipe=recipe, max_cost_usd=5).wait()
run.deploy()  # Or download LoRA weights for vLLM / SGLang
```

Two examples are enough to see the whole loop, and the plan will warn that they are too few to train a useful model. For a real run, pass a file or a Hugging Face dataset instead of a list: `client.datasets.push("sql", "./train.jsonl")` or `client.datasets.from_hf("HuggingFaceH4/ultrachat_200k", split="train_sft")`.

### Versioning and deprecations

The SDKs follow semantic versioning, so upgrading within a major version shouldn't break your code:

- **Patch releases only fix bugs.**
- **Renamed APIs keep their old name for at least two minor releases**, with a `DeprecationWarning` that names the replacement. Removed CLI commands print what replaced them.
- **Release notes always have New, Deprecated and Breaking sections**, with a migration example for every breaking change.
- **Changes to how `"auto"` defaults resolve are versioned**, so an existing run config keeps training the same way.

Base model retirement follows its own notice policy; see [Model retirement](/docs/training/models/#model-retirement).

## Use your deployed model and log outcomes

`run.deploy()` (and `grad deploy`) hosts your artifact on Gradiated Cloud under `your-org/<name>`, so you can call it with the OpenAI, Anthropic, or SystemOne SDK (or `client.route(...)` for routers). If you prefer to self-host serving, download the LoRA weights with `grad artifacts download` and load them into vLLM or SGLang.

<DocsCodeTabs>
  <DocsCodeTab label="Chat model (OpenAI SDK)">

```python
import os
from openai import OpenAI
from grad import Grad

client = Grad()
oai = OpenAI(base_url="https://api.gradiated.com/v1", api_key=os.environ["GRADIATED_API_KEY"])

raw = oai.chat.completions.with_raw_response.create(
    model="your-org/sql-helper",
    messages=[{"role": "user", "content": "Count active users from yesterday."}],
)
inference_id = raw.headers["x-gradiated-inference-id"]
sql = raw.parse().choices[0].message.content

# Log the real outcome: it updates deployment quality metrics and becomes data for your next run
query_succeeded = sql.strip().upper().startswith("SELECT")  # replace with your own check, e.g. the query ran
client.feedback.record(
    inference_id=inference_id,
    idempotency_key=f"query-{inference_id}",
    score=1.0 if query_succeeded else 0.0,
)
```

from openai import OpenAI
from grad import Grad

)

## Two ways to train

Start with a built-in `Recipe` and its defaults. Learning rate, batch size and schedule are calibrated for each base model, and the dry run prints every resolved value. When you need more control, override a single piece (like the loss function or dataset split), or write your own Python loop directly on `Trainer`.

| Mode | How it works | When to use it |
| --- | --- | --- |
| [**Recipes**](/docs/training/recipes/) | Pick a recipe (`RouterRecipe`, `DecisionModelRecipe`, `SFTRecipe`, `DPORecipe`, `GRPORecipe`, `DistillRecipe`, `CartridgeRecipe`, `RewardModelRecipe`, `EmbeddingRecipe`), chain stages with `.then(...)`, or run from YAML. | Almost always, including multi-turn agent RL (`GRPORecipe(env=...)`). You get calibrated defaults, held-out evaluations, automatic checkpoints, and can swap individual pieces without writing a training loop. |
| [**Custom loops**](/docs/training/custom-loops/) | Call `Trainer`, `Artifact`, `Environment`, and `Rubric` directly in Python with built-in losses or your own PyTorch `CustomLoss`. | You are building a new algorithm: a custom research loop, multi-trainer setup, replay buffer, or rollout logic a recipe can't express. |

You can export the full resolved config of any run as YAML (`grad runs inspect <run_id> --yaml > recipe.yaml`) to check it into Git.

<DocsCallout label="Pay only for tokens trained" tone="tip">
You pay per million tokens processed (training and sampling) plus storage for saved artifacts and checkpoints. You never pay for idle GPUs. Start with the simplest option that proves value: a router or decision model trains quickly, then move up to fine-tuning or RL once you have a baseline.
</DocsCallout>

## Using with coding agents

Every docs page includes a **Copy** menu (**Copy page** as raw Markdown or **Copy prompt** for coding agents) in the top right, and every page is served as plain Markdown at `<url>.md`, indexed in [`/llms.txt`](/llms.txt) and `/llms-full.txt`.

The CLI is designed for non-interactive agent loops: pass `--json` to any `grad` command for a single JSON envelope on stdout, and run `--dry-run --json` (or `client.runs.plan(...)`) to validate dataset coverage and estimate tokens and cost before starting a run.

### Starter prompts to paste into Claude Code, Codex, or Cursor

<DocsCodeTabs>
  <DocsCodeTab label="Model router">

```text
Read https://gradiated.com/docs/training/recipes/router.md and integrate a Gradiated model router into this codebase:
1. Find where we call LLMs and inspect how we log or store completed requests and outcomes.
2. Push or import historical traces into a Gradiated dataset using GRADIATED_API_KEY from env.
3. Run `grad train --dataset <name> --name <router> --recipe router --dry-run --json` first and fix any data warnings.
4. Train the router, verify `eval_report.pareto_summary.quality_drop_ci95` stays inside 2%, and deploy with `grad deploy <router>@latest`.
5. Wire `client.route("<router>", ...)` (or pass `model="your-org/<router>"` to the OpenAI/Anthropic SDK) and `client.feedback.record(...)` with idempotency keys.
```

  </DocsCodeTab>
  <DocsCodeTab label="Fine-tune (SFT & DPO)">

```text
Read https://gradiated.com/docs/training/recipes/sft.md (and https://gradiated.com/docs/training/recipes/dpo.md) and set up a fine-tuning pipeline for our task:
1. Export verified passing examples as plain chat records (`{"messages": [...]}`, last assistant turn is the target) and push them with `client.datasets.push(name, records_or_jsonl_path)`.
2. Score the dataset with a `Judge` (`dataset.score(judge).wait()`), keep high scorers with `dataset.filter(scores={"clean": ">=0.8"})`, and configure `SFTRecipe(model="qwen/qwen3-8b")` with its defaults (chain into `DPORecipe` with `.then(...)` if needed). Don't hand-set `lr`; the default `lr="auto"` is calibrated per model.
3. Run `grad render <dataset> --model qwen/qwen3-8b --limit 3` to check the chat template and loss mask, then `client.runs.plan(...)` or `grad train -f recipe.yaml --dry-run --json` and fix every warning.
4. Start the run with `max_cost_usd=` set, deploy with `run.deploy()` (or download the LoRA for vLLM/SGLang), and wire `feedback.record()` so human fixes are captured as `expected_output`.
```

  </DocsCodeTab>
  <DocsCodeTab label="RL agent (Docker Compose)">

```text
Read https://gradiated.com/docs/training/environments.md and https://gradiated.com/docs/training/recipes/rl-agents.md:
1. If our agent is a set of Python tool functions, wrap them with `environments.Tools([...], tasks=dataset, rubric=rubric)`. Otherwise subclass `grad.Environment` around our existing `docker-compose.yml` (only `setup` and `step` are required; `step` gets parsed `action.tool_calls`).
2. Write a `Rubric` with deterministic `StatefulScorer` assertions against the live container state.
3. Smoke-test 2 tasks with `client.evals.create(model="qwen/qwen3-8b", tasks=..., env=env, samples=2)` and check that tool outputs are masked and containers clean up.
4. Train with the managed `GRPORecipe(model="qwen/qwen3-8b", env=env)` and its defaults; run `client.runs.plan(...)` first and set `max_cost_usd=`. If containers must stay on our infra, run `grad env serve` and pass `env=environments.Remote(...)`.
```

  </DocsCodeTab>
  <DocsCodeTab label="Distill / Cartridge">

```text
Read https://gradiated.com/docs/training/recipes/distillation.md (or https://gradiated.com/docs/training/recipes/cartridges.md):
1. Identify our high-volume frontier prompts or repeated long system prompts.
2. Configure `DistillRecipe` (32B teacher -> 4B/8B student) or `CartridgeRecipe` (`adapters.PrefixKV` over our static context).
3. Validate with `client.runs.plan(...)` or `grad train -f recipe.yaml --dry-run --json`, run training, compare `eval_report` against the baseline, and deploy with `grad deploy`.
```
