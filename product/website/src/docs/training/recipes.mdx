# Recipes

<DocsLead>Pick a recipe, check the cost with a dry run, and train with sensible defaults.</DocsLead>

A **recipe** is a Python class that wires up a common training workflow (`RouterRecipe`, `DecisionModelRecipe`, `SFTRecipe`, `DPORecipe`, `GRPORecipe`, `DistillRecipe`, `CartridgeRecipe`, `RewardModelRecipe`, `EmbeddingRecipe`). When a run finishes, it saves a versioned `.grad` [`Artifact`](/docs/training/artifacts/) along with its held-out evaluation report.

<DocsRecipeChooser />

## Built-in recipes

| Recipe class | Guide | Expected dataset fields |
| --- | --- | --- |
| `RouterRecipe` | [Model router](/docs/training/recipes/router/) | Prompts (`messages`) + a `rubric=` (such as a `Judge`) or existing `scores` (optional `metrics.cost_usd`) |
| `DecisionModelRecipe` | [Decision models](/docs/training/recipes/decision-model/) | SystemOne `state` + `questions` (`choice`, `noul`, `score`) and `expected_output` |
| `SFTRecipe` | [Supervised fine-tuning (SFT)](/docs/training/recipes/sft/) | Chat records (`{"messages": [...]}`, last assistant turn is the target), or `input` + `expected_output` |
| `DPORecipe` | [Preference tuning (DPO)](/docs/training/recipes/dpo/) | `prompt` + `chosen` + `rejected` records, or paired `group_id` trajectories |
| `GRPORecipe` | [RL for agents](/docs/training/recipes/rl-agents/) | Tasks + a [`Rubric`](/docs/training/rubrics/), or any [`Environment`](/docs/training/environments/), single- or multi-turn |
| `DistillRecipe` | [Model distillation](/docs/training/recipes/distillation/) | Prompts or traces + `teacher` model |
| `CartridgeRecipe` | [Context Cartridges](/docs/training/recipes/cartridges/) | Static corpus (`Context`) + QA prompts (`num_tokens`) |
| `RewardModelRecipe` | [Reward models](/docs/training/recipes/reward-models/) | `prompt` + `chosen` + `rejected` records, or paired `group_id` trajectories |
| `EmbeddingRecipe` | [Embeddings](/docs/training/recipes/embeddings/) | `Triplet` examples (`query`, `positive` doc, optional `negatives`) |

Any dataset works as input: a list of plain chat records or a `.jsonl` file (`client.datasets.push(name, records_or_path)`), a Hugging Face dataset (`client.datasets.from_hf(...)`), or traces imported from your observability tool. See [Trajectories](/docs/training/trajectories/).

## Start with recipe defaults

Every recipe comes with working defaults for the base model, train/eval split, learning rate, batch size, schedule, checkpoints and evals. You pay per million tokens trained plus storage for saved weights, so you don't pay for idle GPUs. Pass your dataset, output name, and recipe, and use `--dry-run` (or `runs.plan()`) to check data coverage and estimated cost before launching. Set `max_cost_usd=` on any run to cap spend. You can also attach `loggers=[loggers.WandB(project="...")]` or `loggers.MLflow(...)` and inspect live completions with `grad runs logs <run_id> --samples 5` (see [Tuning & troubleshooting](/docs/training/tuning-troubleshooting/)).

<DocsCodeTabs action={<DocsApiKeyAction />}>
  <DocsCodeTab label="Python">

```python
from grad import Grad

dataset = client.datasets.get("support-prod")

# Optional pre-flight check before starting training ($0)
plan = client.runs.plan(dataset=dataset, name="support-router", recipe=RouterRecipe())
print(plan.resolved_recipe, plan.warnings, plan.estimated_tokens, plan.estimated_cost_usd)

run = client.runs.create(
    dataset=dataset,
    name="support-router",
    recipe=RouterRecipe(),
    max_cost_usd=20,  # stops gracefully and saves a checkpoint if reached
).wait(
    on_metric=lambda m: print(f"step={m.step} loss={m.loss:.4f}"),
)

print(run.artifact.id)
print(run.eval_report)
```

### Defaults every recipe resolves

You don't need to set any of these. The dry run prints the value each one resolved to, and any argument you pass wins.

| Setting | Default | How it's chosen |
| --- | --- | --- |
| `model` | `qwen/qwen3-8b` (`qwen/qwen3-0.6b` for routers) | Any trainable base model or a previous `Artifact`. See [Supported models](/docs/training/models/). |
| `lr` | `"auto"` | Calibrated per base model, objective, adapter and batch size. Typical values for `qwen/qwen3-8b`: SFT `5e-4`, DPO `2e-5`, GRPO `5e-5`. See [Tuning & troubleshooting](/docs/training/tuning-troubleshooting/#learning-rate). |
| `adapter` | `adapters.LoRA(rank=32)` | `alpha` is fixed at `32`, so changing the rank doesn't change the right learning rate. |
| `optimizer` | `optim.AdamW(betas=(0.9, 0.95), weight_decay=0.0, grad_clip=1.0)` | Standard settings for LoRA and RL; you rarely need to change them. |
| `schedule`, `warmup` | `"linear"`, `0.03` | Linear decay to zero after 3% warmup. |
| `batch_size`, `epochs` | `128`, `1` (SFT) · `32` prompts × `group_size=8` (GRPO) | The plan warns when a run has fewer than 100 steps. |
| `max_new_tokens` (RL, distillation) | `"auto"` | p95 completion length of the base model on 64 of your prompts, measured during the plan. Metrics report `truncation_rate`. |
| `loss` (GRPO) | `"auto"` | `losses.GRPO(clip_low=0.2, clip_high=0.28)` on-policy; `losses.CISPO(...)` when `max_staleness > 0`. |
| `thinking`, `train_on` | `"auto"`, `"last"` | How the chat template is rendered and which assistant turns are trained. Preview with `grad render`. |
| Checkpoints | every 10% of steps, and at least every 20 steps | Includes optimizer state. Kept 30 days unless promoted to an `Artifact`. Resume with `client.runs.resume(run_id)`. |
| `eval_every`, `select` | `"auto"` (10% of steps), `"best"` | `run.artifact` is the best checkpoint by held-out eval; pass `select="last"` to keep the final one. |
| `max_cost_usd` | none | Stops the run gracefully, saves a checkpoint, and marks it `stopped: budget`. |

## Where your code runs

Managed runs execute on Gradiated's servers, so closing your laptop never stops them. That works for your own Python code too:

- **Built-in specs run on Gradiated's servers:** `Rubric` checks, `Judge`, `validators.*` (regex, JSON schema, SQL, exact and numeric match), and built-in environments (`environments.Tools`, `Harbor`, remote `MCP` servers by URL, and [verifiers](/docs/training/environments/) Hub environments).
- **Your Python functions are packaged automatically.** When a managed run starts, the SDK uploads the source of each function you passed (a `Scorer(fn=...)`, a `rubric=` function, a custom `Environment` subclass) with the `requirements=[...]` you declare, and runs it in an isolated sandbox with no network access unless you set `network=True`. `runs.plan()` packages everything before anything is billed and fails with a specific message if a function can't be packaged, for example because it reads a local file or captures a database connection from your script.
- **Need it on your machine?** Pass `runtime="local"` and keep `grad worker` running wherever the code has access to what it needs. The run pauses while no worker is connected and resumes when one reconnects. For environments, `grad env serve` does the same for rollout workers (see [Environments](/docs/training/environments/)).
- **Filtering data:** field filters such as `dataset.filter(scores={"resolved": ">=0.8"})` run on the server with no download. `dataset.filter(fn)` with a Python function runs on your machine when you call it and saves the selected IDs as a server-side view, so no trajectories are copied.

```python
import re
import requests
from grad import Rubric, Scorer

def cites_ticket(traj) -> float:
    return 1.0 if re.search(r"TICKET-\d+", traj.output.text) else 0.0

def reads_well(traj) -> float:
    import textstat
    return min(textstat.flesch_reading_ease(traj.output.text) / 60, 1.0)

def ticket_exists(traj) -> float:
    # Calls a service only your network can reach, so it runs on your machine.
    match = re.search(r"TICKET-\d+", traj.output.text)
    return 1.0 if match and requests.get(f"https://crm.internal.example/tickets/{match.group()}").ok else 0.0

rubric = Rubric([
    Scorer("cites_ticket", fn=cites_ticket),                                       # packaged, runs on Gradiated
    Scorer("reads_well", fn=reads_well, requirements=["textstat==0.7.4"]),          # packaged with its dependency
    Scorer("ticket_exists", fn=ticket_exists, runtime="local", weight=2.0),         # runs on your `grad worker`
])
```

```python
from grad import Grad, Rubric, Scorer, environments, validators
from grad.recipes import GRPORecipe

client = Grad()
tasks = client.datasets.from_hf("openai/gsm8k", subset="main", split="train", prompt="question", answer="answer")

def calculator(expression: str) -> str:
    """Evaluate an arithmetic expression such as '12 * (3 + 4)' and return the result."""
    if not set(expression) <= set("0123456789+-*/(). ") or "**" in expression:
        return "error: use only numbers, spaces and + - * / ( )"
    return str(eval(expression))

env = environments.Tools(
    [calculator],
    tasks=tasks,
    rubric=Rubric([Scorer("correct", fn=validators.NumericMatch(field="answer"))]),
    max_turns=6,
)

# Multi-turn: the model calls the tool as often as it needs, then answers. Same managed recipe.
run = client.runs.create(dataset=tasks, name="gsm8k-calculator", recipe=GRPORecipe(model="qwen/qwen3-4b", env=env)).wait()
```

### Swap one component instead of rewriting the loop

You don't need to write a full training loop just to try a different loss function or split strategy. Pass your own `losses.CustomLoss`, `AdvantageEstimator`, or `Splitter` straight into the recipe. Custom losses are packaged like any other function (see [Where your code runs](#where-your-code-runs)):

```python
import torch
import torch.nn.functional as F
import grad
from grad import losses
from grad.recipes import DPORecipe

class SimPOLoss(losses.CustomLoss):
    """SimPO: reference-free preference loss on length-normalized logprobs."""
    outputs = ("logprobs",)

    def __init__(self, beta: float = 2.0, gamma: float = 0.5):
        self.beta, self.gamma = beta, gamma

    def compute(self, records, out) -> torch.Tensor:
        # records arrive as (chosen, rejected) pairs
        avg = [grad.masked_mean(lp, mask) for lp, mask in zip(out.logprobs, out.masks)]
        chosen, rejected = torch.stack(avg[0::2]), torch.stack(avg[1::2])
        return -F.logsigmoid(self.beta * (chosen - rejected) - self.gamma).mean()

recipe = DPORecipe(model="qwen/qwen3-8b", loss=SimPOLoss(beta=2.0, gamma=0.5))
```

### Run recipes from YAML

Every recipe composed of built-in specs serializes 1:1 to a flat YAML file (`recipe.to_yaml()`) you can check into Git and run from CI. Leave out anything you want at its default:

```yaml
# recipe.yaml
dataset:
  name: diff-merge-prod
  filter:
    scores:
      tests_passed: ">=1.0"
name: fast-diff-merge
recipe: sft
model: qwen/qwen3-8b
adapter:
  kind: lora
  rank: 32
optimizer:
  kind: adamw
  lr: auto
split:
  strategy: by_session
  eval_fraction: 0.10
max_cost_usd: 25
```

```bash
grad train -f recipe.yaml --dry-run
grad train -f recipe.yaml --wait
```

## Chaining stages (`SFT → DPO` / `SFT → GRPO`)

Every recipe takes a model (a base model string or a trained `Artifact`) and produces a new `Artifact`. `run.artifact` can be passed straight into a second run before the first finishes: use `.then(...)` for a simple chain, pass `model=sft.artifact` if you want to branch, or call `.wait()` in between to check metrics before continuing:

<DocsCodeTabs>
  <DocsCodeTab label="Chained (.then)">

```python
from grad import Grad, Judge, Rubric, Scorer, validators
from grad.recipes import GRPORecipe, SFTRecipe

client = Grad()
gold_ds = client.datasets.get("diff-merge-gold")
tasks_ds = client.datasets.get("diff-merge-tasks")

merge_rubric = Rubric([
    Scorer("valid_ts", weight=0.4, fn=validators.TypeScriptAST()),
    Judge(
        name="exact_merge",
        model="{{SONNET_MODEL}}",
        prompt="Verify the merged file applies the edit cleanly without breaking surrounding code.",
        weight=0.6,
    ),
])

# GRPO starts automatically when SFT finishes and cancels if SFT fails.
run = (
    client.runs.create(
        dataset=gold_ds,
        name="fast-diff-merge",
        recipe=SFTRecipe(model="qwen/qwen3-8b"),
    )
    .then(
        dataset=tasks_ds,
        recipe=GRPORecipe(rubric=merge_rubric),  # model and adapter come from the SFT stage; lr re-resolves for RL
    )
    .wait()
)
```

  </DocsCodeTab>
  <DocsCodeTab label="Pass run.artifact (or inspect in between)">

```python
from grad import Grad, Judge
from grad.recipes import GRPORecipe, SFTRecipe

client = Grad()

    dataset=tasks_ds,
    name="fast-diff-merge",
    recipe=GRPORecipe(
        model=sft.artifact,
        rubric=merge_rubric,
    ),
).wait()
```

## When to write a custom loop

Stick with a `Recipe` (even with a custom loss, splitter, or a multi-turn `Environment`) as long as a standard train/eval flow works. Multi-turn agent RL, Docker Compose environments and async rollouts all run in the managed `GRPORecipe`. Switch to [custom loops](/docs/training/custom-loops/) only when you are building a new algorithm:

- Multiple trainers updating together in one loop (like a separate actor and critic).
- Custom rollout setups like replay buffers, tree search, or multi-agent self-play.
- Manual control over batching and mid-run `trainer.snapshot()` calls.
