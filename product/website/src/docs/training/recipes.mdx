# Recipes

<DocsLead>Pick a composable recipe class, start with sensible defaults, validate token volume with a dry run, and swap any adapter, loss, splitter, or optimizer without rewriting a training loop.</DocsLead>

Every **recipe** (`RouterRecipe`, `ClassifierRecipe`, `SFTRecipe`, `DPORecipe`, `GRPORecipe`, `DistillRecipe`, `CartridgeRecipe`) is an open, inspectable Python class composed from typed building blocks (`adapters.*`, `losses.*`, `optim.*`, `splits.*`, `solvers.*`, `calibration.*`) on top of the five core primitives. Every completed run writes an immutable `.grad` [`Artifact`](/docs/training/endpoints/) alongside its `EvalReport`.

<DocsRecipeChooser />

## Built-in recipes

| Recipe class | Guide | Expected dataset fields |
| --- | --- | --- |
| `RouterRecipe` | [Model router](/docs/training/recipes/router/) | Multi-model traces with `scores`, `metrics.cost_usd`, and `metadata.model` |
| `ClassifierRecipe` | [Classifiers and decisions](/docs/training/recipes/classifier/) | `expected_output.label` or `scores` (binary, multiclass, ordinal) |
| `SFTRecipe` | [Fine-tuning and preferences](/docs/training/recipes/sft-dpo/) | `input` + `expected_output` (or filtered high-score `output`) |
| `DPORecipe` | [Fine-tuning and preferences](/docs/training/recipes/sft-dpo/) | Paired `group_id` trajectories with `role: chosen \| rejected` |
| `GRPORecipe` | [RL for agents (GRPO)](/docs/training/recipes/rl-agents/) | Prompts + a `Rubric`, `WebhookRubric`, or stateful `Environment` |
| `DistillRecipe` | [Distillation and Cartridges](/docs/training/recipes/distillation/) | Prompts or traces + `teacher` artifact |
| `CartridgeRecipe` | [Distillation and Cartridges](/docs/training/recipes/distillation/) | Static context corpus + QA prompts (`adapters.PrefixKV`) |

For specialized training patterns built on these same primitives, see [Reward models and verifiers](/docs/training/recipes/reward-models/) and [Embeddings and rerankers](/docs/training/recipes/embeddings/).

## Start with recipe defaults

Every recipe ships with working defaults for base model, train/eval split, optimizer, and calibration. Training is billed **per million tokens processed** plus storage for saved weights — never idle GPU time. Pass your dataset, output name, and recipe, then run `--dry-run` (or `runs.plan()`) to verify data coverage and estimated tokens before starting a run.

<DocsCodeTabs action={<DocsApiKeyAction />}>
  <DocsCodeTab label="Python">

```python
from grad import Grad
from grad.recipes import RouterRecipe

client = Grad()

# Optional pre-flight check before starting training ($0)
plan = client.runs.plan(dataset="support-prod", name="support-router", recipe=RouterRecipe())
print(plan.resolved_recipe, plan.warnings, plan.estimated_tokens, plan.estimated_cost_usd)

run = client.runs.create(
    dataset="support-prod",
    name="support-router",
    recipe=RouterRecipe(),
).wait(
    on_metric=lambda m: print(f"step={m.step} loss={m.loss:.4f}"),
)

print(run.artifact.id)
print(run.eval_report)
```

## Compose and customize recipes

Every component is a typed dataclass (`adapters.*`, `optim.*`, `calibration.*`) or an extensible interface (`losses.*`, `solvers.*`, `splits.*`, `Rubric`). Omit any argument to keep its default — or swap in your own subclass or Python callable when you want custom behavior without rewriting the loop.

<DocsCodeTabs>
  <DocsCodeTab label="Router">

```python
from grad import Grad, calibration, solvers, splits
from grad.recipes import RouterRecipe

client = Grad()

recipe = RouterRecipe(
    model="BAAI/bge-small-en-v1.5",
    solver=solvers.DualHeadKernelLBFGS(l2=0.1),
    score_key="task_success",
    split=splits.BySession(eval_fraction=0.15),
    calibration=calibration.SLA(max_quality_drop=0.02),
)

run = client.runs.create(dataset="support-prod", name="support-router", recipe=recipe).wait()
```

  </DocsCodeTab>
  <DocsCodeTab label="Classifier">

```python
from grad import Grad, calibration, losses, splits
from grad.recipes import ClassifierRecipe

client = Grad()

recipe = ClassifierRecipe(
    model="BAAI/bge-small-en-v1.5",
    labels=["low", "medium", "high"],
    loss=losses.OrdinalBCE(),
    calibration=calibration.Temperature(),
    split=splits.BySession(eval_fraction=0.10),
)

run = client.runs.create(dataset="coding-effort-labels", name="coding-effort", recipe=recipe).wait()
```

  </DocsCodeTab>
  <DocsCodeTab label="SFT">

### Swap one component instead of rewriting the loop

Because every recipe accepts any `Loss` (built-in or `losses.CustomLoss`), any `AdvantageEstimator`, or any `Splitter`, tweaking a research objective is a single constructor argument — no need to drop down to a full manual loop just to change a loss formula:

```python
# Swap built-in losses.DPO() for your own SimPOLoss subclass inside DPORecipe:
recipe = DPORecipe(
    model="Qwen/Qwen3-8B",
    adapter=adapters.LoRA(rank=32),
    loss=SimPOLoss(beta=2.0, gamma=0.5),
    optimizer=optim.AdamW(lr=3e-5),
)
```

### Run recipes from YAML

Every recipe composed of built-in specs serializes 1:1 to a flat YAML file (`recipe.to_yaml()`) you can check into Git and run from CI:

```yaml
# recipe.yaml
dataset: diff-merge-prod
name: fast-diff-merge
recipe: sft
model: Qwen/Qwen3-8B
adapter:
  kind: lora
  rank: 32
optimizer:
  kind: adamw
  lr: 2e-4
split:
  strategy: by_session
  eval_fraction: 0.10
filter:
  min_score:
    tests_passed: 1.0
merge_adapter: true
```

```bash
grad train -f recipe.yaml --dry-run
grad train -f recipe.yaml --wait
```

## Multi-stage pipelines (`SFT → DPO` / `SFT → GRPO`)

Every `Recipe` transforms an input `Artifact` into a new immutable `Artifact` (`model=` accepts either a base model ID or a trained `Artifact`). You can chain stages imperatively when you want to inspect metrics in between, or compose them into a single server-side `Pipeline`:

<DocsCodeTabs>
  <DocsCodeTab label="Declarative Pipeline">

```python
from grad import Grad, Pipeline, Stage, WebhookRubric, adapters, optim
from grad.recipes import GRPORecipe, SFTRecipe

client = Grad()

pipe = Pipeline(
    model="Qwen/Qwen3-8B",
    name="fast-diff-merge",
    stages=[
        Stage(
            dataset="diff-merge-gold",
            recipe=SFTRecipe(adapter=adapters.LoRA(rank=32), optimizer=optim.AdamW(lr=2e-4)),
        ),
        Stage(
            dataset="diff-merge-tasks",
            recipe=GRPORecipe(
                adapter=adapters.LoRA(rank=32),
                rubric=WebhookRubric(url="https://ci.internal.example/grade-diff", secret="grader-webhook-token"),
                optimizer=optim.AdamW(lr=2e-5),
            ),
        ),
    ],
)

plan = client.runs.plan(pipe)          # validates both stages + total token/cost estimate ($0)
run = client.runs.create(pipe).wait()  # stage 1 artifact flows directly into stage 2 on the server
```

  </DocsCodeTab>
  <DocsCodeTab label="Imperative (inspect between stages)">

```python
sft = client.runs.create(
    dataset="diff-merge-gold",
    name="fast-diff-merge",
    recipe=SFTRecipe(model="Qwen/Qwen3-8B", adapter=adapters.LoRA(rank=32)),
).wait()

# Inspect sft.eval_report, then pass sft.artifact directly as `model=`
rl = client.runs.create(
    dataset="diff-merge-tasks",
    name="fast-diff-merge",
    recipe=GRPORecipe(
        model=sft.artifact,
        rubric=WebhookRubric(url="https://ci.internal.example/grade-diff", secret="grader-webhook-token"),
    ),
).wait()
```

</DocsCodeTabs>

## Live metrics and evaluation

Stream step-by-step telemetry (`step`, `loss`, `grad_norm`, `lr`, `tokens_per_sec`, `eval_metrics`) while a run is active, or inspect the saved `eval_report.json` afterward:

  <DocsCodeTab label="Python">

```python

    print(metric.step, metric.loss, metric.eval_metrics)
```

  </DocsCodeTab>
  <DocsCodeTab label="TypeScript">

```ts
for await (const metric of grad.runs.metrics(run.id, { follow: true })) {
```

Router artifacts include a held-out cost-vs-quality Pareto curve and 95% bootstrap confidence intervals against your fallback model.

## When to write a custom loop

Stay with `Recipe` (including swapping in a `CustomLoss` or custom `Splitter`) while a standard train/eval lifecycle fits your task. Drop down to [custom loops](/docs/training/custom-loops/) when you need:

- Multiple co-evolving `Trainer` instances in one loop (e.g. online actor + critic or implicit PRM).
- Custom rollout topologies such as async replay buffers, Monte Carlo prefix branching, or multi-agent self-play.
- Full imperative control over microbatch scheduling, mid-loop `trainer.snapshot()` mining, or stateful Docker Compose rollouts.
