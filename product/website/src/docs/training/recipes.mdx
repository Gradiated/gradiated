# Recipes

<DocsLead>
  Pick a recipe, check the cost with a dry run, and train with sensible
  defaults.
</DocsLead>

A **recipe** is a Python class that wires up a common training workflow (`RouterRecipe`, `DecisionModelRecipe`, `SFTRecipe`, `DPORecipe`, `CartridgeRecipe`, `EmbeddingRecipe`). When a run finishes, it saves a versioned `.grad` [`Artifact`](/docs/training/artifacts/) along with its held-out evaluation report.

<DocsRecipeChooser />

## Built-in recipes

| Recipe class          | Guide                                                       | Expected dataset fields                                                                                   |
| --------------------- | ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `RouterRecipe`        | [Model router](/docs/training/recipes/router/)              | Prompts (`messages`) + a `rubric=` (such as a `Judge`) or existing `scores` (optional `metrics.cost_usd`) |
| `DecisionModelRecipe` | [Decision models](/docs/training/recipes/decision-model/)   | SystemOne `state` + `questions` (`choice`, `noul`, `score`) and `expected_output`                         |
| `SFTRecipe`           | [Supervised fine-tuning (SFT)](/docs/training/recipes/sft/) | Chat records (`{"messages": [...]}`, last assistant turn is the target), or `input` + `expected_output`   |
| `DPORecipe`           | [Preference tuning (DPO)](/docs/training/recipes/dpo/)      | `prompt` + `chosen` + `rejected` records, or paired `group_id` trajectories                               |
| `CartridgeRecipe`     | [Context Cartridges](/docs/training/recipes/cartridges/)    | Static corpus (`Context`) + QA prompts (`num_tokens`)                                                     |
| `EmbeddingRecipe`     | [Embeddings](/docs/training/recipes/embeddings/)            | `Triplet` examples (`query`, `positive` doc, optional `negatives`)                                        |

[RL for agents](/docs/training/recipes/rl-agents/) (`GRPORecipe`), [distillation](/docs/training/recipes/distillation/) (`DistillRecipe`) and [reward models](/docs/training/recipes/reward-models/) (`RewardModelRecipe`) arrive in Wave 2.

Any dataset works as input: a list of plain chat records or a `.jsonl` file (`client.datasets.push(name, records_or_path)`), a Hugging Face dataset (`client.datasets.from_hf(...)`), or traces imported from your observability tool. See [Trajectories](/docs/training/trajectories/).

## Start with recipe defaults

Every recipe comes with working defaults for the base model, split, learning rate, batch size, schedule, checkpoints and evals. Pass your dataset, an output name and the recipe. Run `--dry-run` (or `runs.plan()`) first to check your data and see the estimated cost, and set `max_cost_usd=` to cap spend. You pay per million tokens trained plus storage for saved weights, never for idle GPUs.

<DocsCodeTabs action={<DocsApiKeyAction />}>
  <DocsCodeTab label="Python">

```python
from grad import Grad
from grad.recipes import RouterRecipe

client = Grad()
dataset = client.datasets.get("support-prod")

# Optional pre-flight check before starting training ($0)
plan = client.runs.plan(dataset=dataset, name="support-router", recipe=RouterRecipe())
print(plan.resolved_recipe, plan.warnings, plan.estimated_tokens, plan.estimated_cost_usd)

run = client.runs.create(
    dataset=dataset,
    name="support-router",
    recipe=RouterRecipe(),
    max_cost_usd=20,  # stops gracefully and saves a checkpoint if reached
).wait(
    on_metric=lambda m: print(f"step={m.step} loss={m.loss:.4f}"),
)

print(run.artifact.id)
print(run.eval_report)
```

  </DocsCodeTab>

### Preview with `--dry-run` before training

Before spending anything, run `--dry-run` (or `client.runs.plan()`) to check your dataset for unusable or truncated records and too few training steps, see every resolved default, and get a token and cost estimate:

<DocsTerminal
  title="Pre-flight dry run ($0)"
  command="grad train --dataset diff-merge-prod --name fast-diff-merge --recipe sft --dry-run"
>

```text
  records   : 11,840 usable of 14,200

  steps     : 84 (batch 128, 1 epoch)
  lr        : 5.0e-4 (auto@2: calibrated for qwen/qwen3-8b at batch 128, sqrt batch scaling)
  tokens    : ~38.0M (31.0% trained)

  adapter   : kind=lora, rank=32, alpha=32, merge_on_export=false

  Start it by re-running without --dry-run (add --wait to follow it).
```

### Defaults

You don't need to set anything beyond `model=`. Learning rate, adapter, batch size, schedule, checkpoints and evals all resolve automatically, and the dry run above prints each value. Anything you pass overrides the default. The full list, and how each `"auto"` value is chosen, is in the [training parameters reference](/docs/reference/training-parameters/#common-run-parameters).

### Inspect resolved defaults

Export the full resolved config of any run as YAML to see every default (model, split strategy and hyperparameters) and check it into Git:

```bash
grad runs inspect run_01J9X --yaml > recipe.yaml
```

## Where your code runs

Managed runs execute on Gradiated's servers, so closing your laptop never stops them. Rubric checks run in one of two places:

- **Built-in checks run on Gradiated's servers:** `Judge` and the built-in `validators` (`JSON`, `NonEmpty`, `ExactMatch`, `Regex`).
- **Your Python functions run in your own process.** In an [evaluation](/docs/training/evaluations/), a `Scorer(fn=...)` runs where you call `ev.wait()`: the SDK pulls the model outputs, calls your function and posts the scores. `requirements=[...]` is checked against your installed packages before the eval starts.
- **Training recipes take built-in checks only.** `RouterRecipe(rubric=...)` accepts a `Judge`, validators, or the name of a score already on your records. Python functions inside training recipes arrive in Wave 2.

Details are in the [reference](/docs/reference/training-parameters/#where-code-runs).

```python
import re
from grad import Judge, Rubric, Scorer, validators

def cites_ticket(traj) -> float:
    return 1.0 if re.search(r"TICKET-\d+", traj.output.text) else 0.0

rubric = Rubric([
    Judge(name="resolved", model="{{SONNET_MODEL}}", prompt="Did the assistant resolve the issue?"),  # server
    Scorer("not_empty", fn=validators.NonEmpty()),                                                    # server
    Scorer("cites_ticket", fn=cites_ticket, weight=2.0),                                              # your process
])
```

## Customize any piece

Leave out any argument to keep the recipe's default, or override just the pieces you care about (`model`, `adapter`, `loss`, `optimizer`, `split`, `rubric`):

<DocsCodeTabs>
  <DocsCodeTab label="Router">

```python
from grad import Grad, Judge
from grad.recipes import RouterRecipe

client = Grad()
dataset = client.datasets.get("support-prod")

recipe = RouterRecipe(
    model="qwen/qwen3-0.6b",
    models=["qwen/qwen3-8b", "{{OPUS_MODEL}}"],
    rubric=Judge(
        name="resolved",
        model="{{SONNET_MODEL}}",
        prompt="Did the assistant solve the user's issue accurately?",
    ),
)

run = client.runs.create(dataset=dataset, name="support-router", recipe=recipe).wait()
```

  </DocsCodeTab>
  <DocsCodeTab label="Decision model">

```python
from grad import Grad, splits
from grad.recipes import DecisionModelRecipe

client = Grad()
dataset = client.datasets.get("ticket-triage")

recipe = DecisionModelRecipe(
    model="gradiated/linden-1",
    split=splits.BySession(eval_fraction=0.15),
)

run = client.runs.create(dataset=dataset, name="ticket-triage", recipe=recipe).wait()
```

  </DocsCodeTab>
  <DocsCodeTab label="SFT">

```python
from grad import Grad, adapters
from grad.recipes import SFTRecipe

client = Grad()
dataset = client.datasets.get("diff-merge-prod")

recipe = SFTRecipe(
    model="qwen/qwen3-8b",
    adapter=adapters.LoRA(rank=64),  # large dataset (>50k records): a higher rank helps
)

run = client.runs.create(dataset=dataset, name="fast-diff-merge", recipe=recipe).wait()
```

  </DocsCodeTab>
  <DocsCodeTab label="DPO">

```python
from grad import Grad, losses
from grad.recipes import DPORecipe

client = Grad()
dataset = client.datasets.get("support-preferences")
sft_art = client.artifacts.get("support-responder-sft@latest")

recipe = DPORecipe(
    model=sft_art,               # continues the SFT artifact's adapter
    loss=losses.DPO(beta=0.3),   # default 0.1; a higher beta stays closer to the SFT model
)

run = client.runs.create(dataset=dataset, name="support-responder", recipe=recipe).wait()
```

  </DocsCodeTab>

### Run recipes from YAML

A run config is a flat YAML file (`grad runs inspect RUN --yaml` writes one) that you can check into Git and run from CI. Leave out anything you want at its default:

```yaml
# recipe.yaml
dataset: diff-merge-prod
name: fast-diff-merge
recipe: sft
model: qwen/qwen3-8b
adapter:
  kind: lora
  rank: 64
```

```bash
grad train -f recipe.yaml --dry-run
grad train -f recipe.yaml --wait
```

## Train in stages (`SFT → DPO`)

Every recipe takes a model (a base model string or a trained `Artifact`) and produces a new `Artifact`. To run DPO on top of SFT, wait for the SFT run, check its eval report, then pass `sft.artifact` as the DPO recipe's `model`:

<DocsCodeTabs>
  <DocsCodeTab label="Python">

```python
from grad import Grad
from grad.recipes import DPORecipe, SFTRecipe

client = Grad()

sft = client.runs.create(
    dataset=client.datasets.get("support-gold"),
    name="support-responder-sft",
    recipe=SFTRecipe(model="qwen/qwen3-8b"),
).wait()
print(sft.eval_report)  # check SFT before continuing

dpo = client.runs.create(
    dataset=client.datasets.get("support-preferences"),
    name="support-responder",
    recipe=DPORecipe(model=sft.artifact),  # continues the SFT adapter
).wait()
```

  </DocsCodeTab>
  <DocsCodeTab label="TypeScript">

```ts
import { Grad, recipes } from "@gradiated/grad";

const grad = new Grad();

const sft = await grad.runs
  .create({
    dataset: "support-gold",
    name: "support-responder-sft",
    recipe: recipes.sft({ model: "qwen/qwen3-8b" }),
  })
  .wait();
console.log(sft.evalReport);

const dpo = await grad.runs
  .create({
    dataset: "support-preferences",
    name: "support-responder",
    recipe: recipes.dpo({ model: sft.artifact }),
  })
  .wait();
```

  </DocsCodeTab>
  <DocsCodeTab label="Go">

```go
sft, err := client.Runs.Create(ctx, grad.RunParams{
	Dataset: grad.DatasetName("support-gold"),
	Name:    "support-responder-sft",
	Recipe:  grad.SFTRecipe{Common: grad.Common{Model: "qwen/qwen3-8b"}},
}).Wait(ctx)
if err != nil {
	log.Fatal(err)
}
fmt.Println(sft.EvalReport)

dpo, err := client.Runs.Create(ctx, grad.RunParams{
	Dataset: grad.DatasetName("support-preferences"),
	Name:    "support-responder",
	Recipe:  grad.DPORecipe{Common: grad.Common{Model: sft.Artifact.Ref()}},
}).Wait(ctx)
```

  </DocsCodeTab>
  <DocsCodeTab label="CLI">

```bash
grad train --dataset support-gold --name support-responder-sft --recipe sft --model qwen/qwen3-8b --wait
grad train --dataset support-preferences --name support-responder --recipe dpo --model support-responder-sft@latest --wait
```

  </DocsCodeTab>
</DocsCodeTabs>

SFT and DPO runs can continue an SFT or DPO LoRA artifact (not a merged export, `merge_on_export=True`). The adapter's rank and alpha carry over. Router, decision model, cartridge and embedding runs start from a base model. RL on top of an SFT artifact (`GRPORecipe`) arrives in Wave 2; see [RL for agents](/docs/training/recipes/rl-agents/).

## Live metrics and evaluation

Stream step-by-step metrics (loss, eval scores, tokens and cost so far) while a run is active, or inspect the saved `eval_report.json` afterward:

<DocsCodeTabs>
  <DocsCodeTab label="Python">

```python
from grad import Grad

client = Grad()
run = client.runs.get("run_01J9X")

for metric in run.metrics(follow=True):
    print(metric.step, metric.loss, metric.eval_metrics, metric.cost_usd)
```

  </DocsCodeTab>
  <DocsCodeTab label="TypeScript">

```ts
import { Grad } from "@gradiated/grad";

const grad = new Grad();
const run = await grad.runs.get("run_01J9X");

for await (const metric of run.metrics({ follow: true })) {
  console.log(metric.step, metric.loss, metric.evalMetrics);
}
```

  </DocsCodeTab>
  <DocsCodeTab label="CLI">

```bash
grad runs logs run_01J9X --follow
grad artifacts inspect fast-diff-merge@2026-11-25-2 --json
```

  </DocsCodeTab>
</DocsCodeTabs>

Router artifacts include a held-out cost-vs-quality Pareto curve and 95% bootstrap confidence intervals against your fallback model.

## When to write a custom loop

Stick with a `Recipe` as long as a standard train/eval flow works. [Custom loops](/docs/training/custom-loops/) (the `Trainer` API) and custom losses (`losses.CustomLoss`, for example SimPO) arrive in Wave 2. They are for building a new algorithm:

- Multiple trainers updating together in one loop (like a separate actor and critic).
- Custom rollout setups like replay buffers, tree search, or multi-agent self-play.
- Manual control over batching and mid-run `trainer.snapshot()` calls.
