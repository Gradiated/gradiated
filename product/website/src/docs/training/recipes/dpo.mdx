# Preference tuning (DPO)

<DocsLead>
  Teach a model which answers you prefer by showing it pairs of good and bad
  examples.
</DocsLead>

Use **`DPORecipe`** after [Supervised fine-tuning (SFT)](/docs/training/recipes/sft/) when your model already knows the right format but still makes recurring mistakes (like cutting off code, being too wordy, or picking the wrong tool arguments). Showing it **chosen** vs. **rejected** pairs steers it away from those patterns.

## What data you need

- **Minimum volume:** 300–1,000 preference pairs for narrow failure modes; 2,000+ for general style and quality alignment.
- **Format:** the simplest form is one record per pair, with the shared prompt and both answers as chat messages (the same shape as `trl` preference datasets). Pairs always stay together in the same train or eval split.

```json
{
  "prompt": [{ "role": "user", "content": "Merge this diff." }],
  "chosen": [{ "role": "assistant", "content": "clean merged code..." }],
  "rejected": [
    { "role": "assistant", "content": "truncated code with syntax error..." }
  ]
}
```

If your pairs come from production [trajectories](/docs/training/trajectories/), store each side as its own trajectory with a shared `group_id` and `role: "chosen"` or `role: "rejected"`:

```json
[
  {
    "schema": "grad.trajectory/1",
    "group_id": "pair_19",
    "role": "chosen",
    "input": {
      "messages": [{ "role": "user", "content": "Merge this diff." }]
    },
    "output": {
      "turns": [{ "role": "assistant", "content": "clean merged code..." }]
    }
  },
  {
    "schema": "grad.trajectory/1",
    "group_id": "pair_19",
    "role": "rejected",
    "input": {
      "messages": [{ "role": "user", "content": "Merge this diff." }]
    },
    "output": {
      "turns": [
        {
          "role": "assistant",
          "content": "truncated code with syntax error..."
        }
      ]
    }
  }
]
```

## Try it on a public dataset

This runs as pasted. It imports 2,000 preference pairs from Hugging Face and runs DPO with the defaults on top of the base model:

```python
from grad import Grad
from grad.recipes import DPORecipe

client = Grad()
prefs = client.datasets.from_hf(
    "trl-lib/ultrafeedback_binarized",
    split="train",
    chosen="chosen",
    rejected="rejected",
    limit=2000,
)

run = client.runs.create(
    dataset=prefs,
    name="ultrafeedback-dpo",
    recipe=DPORecipe(model="qwen/qwen3-8b"),
).wait()
print(run.artifact.id, run.eval_report)
```

In practice you'll usually run DPO on a model you've already fine-tuned with SFT, as below.

## Train with `DPORecipe`

Pass an existing SFT [`Artifact`](/docs/training/artifacts/) directly as `model=`, or chain `SFTRecipe` into `DPORecipe` with `.then(...)` so DPO starts automatically when SFT finishes:

<DocsCodeTabs action={<DocsApiKeyAction />}>
  <DocsCodeTab label="From an SFT artifact">

```python
from grad import Grad
from grad.recipes import DPORecipe

client = Grad()
sft_art = client.artifacts.get("fast-diff-merge@sft-v1")
prefs = client.datasets.get("diff-merge-preferences")

dpo = client.runs.create(
    dataset=prefs,
    name="fast-diff-merge",
    recipe=DPORecipe(model=sft_art),  # continues training the SFT adapter
).wait()

print(dpo.artifact.id, dpo.eval_report)
```

  </DocsCodeTab>
  <DocsCodeTab label="Chain SFT → DPO (.then)">

```python
from grad import Grad
from grad.recipes import DPORecipe, SFTRecipe

client = Grad()
sft_ds = client.datasets.get("diff-merge-prod").filter(scores={"tests_passed": "==1.0"})
prefs_ds = client.datasets.get("diff-merge-preferences")

dpo = (
    client.runs.create(
        dataset=sft_ds,
        name="fast-diff-merge",
        recipe=SFTRecipe(model="qwen/qwen3-8b"),
    )
    .then(dataset=prefs_ds, recipe=DPORecipe())  # starts from the SFT result
    .wait()
)
```

```ts
import { Grad, recipes } from "@gradiated/grad";

const grad = new Grad();
const sftArt = await grad.artifacts.get("fast-diff-merge@sft-v1");
const prefs = await grad.datasets.get("diff-merge-preferences");

const dpo = await grad.runs
  .create({
    dataset: prefs,
    name: "fast-diff-merge",
    recipe: recipes.dpo({ model: sftArt }),
  })
  .wait();

console.log(dpo.artifact.id, dpo.evalReport);
```

### When to use SFT vs. DPO vs. RL

- **Start with [SFT](/docs/training/recipes/sft/)** when the model doesn't follow your format, schema, or style yet and you have examples of good answers.
- **Follow with DPO (`DPORecipe`)** when the model mostly works but keeps repeating specific mistakes you can show as `(chosen, rejected)` pairs.
- **Move to [RL (`GRPORecipe`)](/docs/training/recipes/rl-agents/)** when you can grade answers automatically with tests, validators, or a judge and want the model to discover better solutions on its own.

### Parameters you might change

- **`loss=losses.DPO(beta=...)`:** `beta` is `0.1` by default. Higher (`0.2`–`0.5`) stays closer to your starting model; lower (`0.05`) pushes harder away from rejected patterns.
- **`lr_scale`:** DPO's learning rate is set automatically and is much lower than SFT's. If held-out preference accuracy climbs fast but your format breaks, pass `lr_scale=0.5`.

When `model=` is an SFT artifact, DPO keeps training that same adapter, and the starting checkpoint is the reference model, so you never load one yourself. Every other setting has a default; see the [training parameters reference](/docs/reference/training-parameters/#dporecipe).

## Deploy

Publish the updated [`Artifact`](/docs/training/artifacts/) on Gradiated Cloud in one line (or download the LoRA adapter for your own vLLM / SGLang servers; see [Deploying](/docs/training/deploying/)):

```python
dpo.deploy()
```

## Want more control?

You can swap `losses.DPO()` for your own PyTorch `losses.CustomLoss` (like SimPO, ORPO, or KTO) right inside `DPORecipe`. See [Custom loops](/docs/training/custom-loops/) and [Advanced objectives](/docs/training/advanced-objectives/).
