# RL for agents

<DocsLead>Train a model with reinforcement learning by grading its answers with code or another model.</DocsLead>

Use **`GRPORecipe`** when you can **grade whether an answer worked** (valid SQL, passing unit tests, right API call) even when there is more than one right way to write it. If the base model doesn't follow your format yet, run a quick [Supervised fine-tuning (SFT)](/docs/training/recipes/sft/) run first and pass that [`Artifact`](/docs/training/artifacts/) as `model=` (or chain them with [`.then(...)`](/docs/training/recipes/)).

## Managed `GRPORecipe` vs. your own `Environment`

| Setup | Use | Why |
| --- | --- | --- |
| **Single-turn prompts + [`Rubric`](/docs/training/rubrics/) (`Judge` / `validators.*`)** | **`GRPORecipe` + `Rubric`** | Give Gradiated a [`Dataset`](/docs/training/trajectories/) of prompts and a `Rubric`; it handles sampling, grading, and training for you. |
| **Multi-turn apps, Harbor, Docker Compose, live DBs** | **[`Environment`](/docs/training/environments/) + [`Trainer`](/docs/training/custom-loops/)** | Your containers and tools stay on your own machines and talk to `Artifact` and `Trainer` over HTTP. |

## Train with `GRPORecipe`

Pass a `Dataset` of prompts and a [`Rubric`](/docs/training/rubrics/) with code checks (`validators.SQL()`, `validators.TypeScriptAST()`, `validators.JSONSchema(...)`) and/or a `Judge` (a frontier `Model` or a fine-tuned [reward model](/docs/training/recipes/reward-models/) `Artifact`):

<DocsCodeTabs action={<DocsApiKeyAction />}>
  <DocsCodeTab label="Python">

```python
from grad import Grad, Judge, Rubric, Scorer, adapters, validators
from grad.recipes import GRPORecipe

client = Grad()
dataset = client.datasets.get("sql-benchmark-tasks")
sft_art = client.artifacts.get("sql-agent@sft-v1")

recipe = GRPORecipe(
    model=sft_art,
    adapter=adapters.LoRA(rank=32),
    rubric=Rubric([
        Scorer("valid_sql", weight=0.3, fn=validators.SQL()),
        Judge(
            name="correct_query",
            model="{{SONNET_MODEL}}",
            prompt="Verify the SQL answers the question accurately without hallucinated columns.",
            weight=0.7,
        ),
    ]),
    group_size=8,
    max_new_tokens=512,
)

run = client.runs.create(dataset=dataset, name="sql-agent", recipe=recipe).wait(
    on_metric=lambda m: print(f"step={m.step} reward={m.eval_metrics.get('mean_reward', 0):.3f}"),
)

print(run.artifact.id)
```

import { Grad, Judge, Rubric, Scorer, adapters, recipes, validators } from "@gradiated/grad";

const grad = new Grad();
const dataset = await grad.datasets.get("sql-benchmark-tasks");
const sftArt = await grad.artifacts.get("sql-agent@sft-v1");

const run = await grad.runs
  .create({
    dataset,
    name: "sql-agent",
    recipe: recipes.grpo({
      model: sftArt,
      adapter: adapters.lora({ rank: 32 }),
      rubric: new Rubric([
        new Scorer("valid_sql", { weight: 0.3, fn: validators.sql() }),
        new Judge({
          name: "correct_query",
          model: "{{SONNET_MODEL}}",
          prompt: "Verify the SQL answers the question accurately without hallucinated columns.",
          weight: 0.7,
        }),
      ]),
      groupSize: 8,
      maxNewTokens: 512,
    }),
  })
  .wait();

console.log(run.artifact.id);

### When to use RL vs. SFT vs. DPO

- **Use [SFT](/docs/training/recipes/sft/)** first if the model doesn't reliably produce valid JSON, SQL, or tool calls yet, since RL works much better once formatting is solid.
- **Use [DPO](/docs/training/recipes/dpo/)** when you already have offline `(chosen, rejected)` pairs and don't need the model to explore new solutions.
- **Use RL (`GRPORecipe`)** when you can grade answers automatically (with code checks, tests, or a `Judge`) and want the model to keep improving beyond your existing examples.

### Key parameters

- **`group_size`:** how many candidate answers the model generates per prompt to compare against each other (`8` is a good default; larger groups give cleaner signal at higher token cost).
- **`max_new_tokens`:** the max length of each generated attempt (like `max_tokens` on an inference call). Set it high enough for the model to finish its answer without getting cut off, and low enough to avoid wasting tokens on rambling outputs.
- **`loss` & `optimizer`:** `GRPORecipe` ships with tuned GRPO defaults (`losses.GRPO()` and `optim.AdamW(lr=2e-5)`). Only override `kl_beta` (e.g. `losses.GRPO(kl_beta=0.05)`) if outputs start drifting away from your starting model's style.

## Practical tips before scaling up

1. **Start with SFT if formatting is shaky:** if the base model outputs broken JSON or tool calls on more than 30% of tries, run a short [SFT](/docs/training/recipes/sft/) job on 200–500 good examples first, then pass `model=sft.artifact`.
2. **Watch for all-pass or all-fail prompts:** if more than 70% of prompts get all `0.0` (too hard) or all `1.0` (too easy), add partial-credit checks to your [`Rubric`](/docs/training/rubrics/) or filter your dataset to medium-difficulty prompts.
3. **Need multi-turn containers or log replay?** See [Environments](/docs/training/environments/) (including `environments.Harbor` and `environments.MCP`) and [Traces to environments](/docs/training/traces-to-environments/).

## Deploy with a fallback cascade

An RL-trained 4B–8B model often matches a frontier model on 80–90% of requests. Pair your [`Artifact`](/docs/training/artifacts/) with a [reward model](/docs/training/recipes/reward-models/) in a `strategies.Cascade` [`Endpoint`](/docs/training/endpoints/) so hard requests fall back to a larger model automatically:

```python
from grad import strategies

agent = client.artifacts.get("sql-agent@2026-11-25-2")
verifier = client.artifacts.get("sql-verifier@v1")
capture = client.datasets.get("sql-agent-prod")

client.endpoints.create(
    slug="sql-agent",
    artifact=agent,
    capture_dataset=capture,
    strategy=strategies.Cascade(
        verifier=verifier,
        frontier="qwen/qwen3-32b",
        threshold=0.75,
    ),
)
```
