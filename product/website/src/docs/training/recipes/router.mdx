# Model router

<DocsLead>
  Send each request to the cheapest model that still meets your quality bar.
</DocsLead>

A model router looks at each incoming prompt and predicts how likely each candidate model is to succeed. At runtime, it picks the cheapest model that still meets your quality bar.

## What data you need

All you need to start is a [`Dataset`](/docs/training/trajectories/) of real prompts (`input.messages`):

- **How the router compares models:**
  - **Already logging multiple models?** If your logs include responses from both cheap and strong models (in `metadata.model`), Gradiated trains directly on them.
  - **Only logging one model so far?** Pass `models=[...]` to `RouterRecipe` (for example, a cheap model and your current frontier model). Gradiated replays your logged prompts against the candidate models first so it can compare how each one performs, with no sandbox environment needed for single-turn prompts.
- **How quality is scored:**
  - **No scores yet?** Pass a [`Judge`](/docs/training/rubrics/) with a plain-English prompt (or a `Rubric` with code checks) and Gradiated grades each response for you.
  - **Already have scores in your logs?** Pass the score name (`rubric="task_success"`) to reuse them directly, or a function (`rubric=lambda t: ...`), which is packaged and run in a sandbox (see [where your code runs](/docs/training/recipes/#where-your-code-runs)).
- **Request cost (optional):**
  - You don't need to log costs. Gradiated calculates request cost automatically from the model name and token counts using built-in model pricing.
  - If you have custom or self-hosted pricing, include `metrics.cost_usd` on your logs to override it.

Plan for ~500 examples per candidate model to get started (2,000+ if your prompts cover many different tasks).

## Train the router

By default, `RouterRecipe` fine-tunes `qwen/qwen3-0.6b` on your prompts and scores, holds out 15% of conversations for evaluation, and routes to stay within a 2% quality drop of your best model. Replaying prompts against candidate models and judging the answers costs money, so run `grad train ... --dry-run` first to see the estimate:

<DocsCodeTabs action={<DocsApiKeyAction />}>
  <DocsCodeTab label="Python">

```python
from grad import Grad, Judge
from grad.recipes import RouterRecipe

client = Grad()
dataset = client.datasets.get("support-traces")

recipe = RouterRecipe(
    models=["qwen/qwen3-8b", "{{OPUS_MODEL}}"],
    rubric=Judge(
        name="resolved",
        model="{{SONNET_MODEL}}",
        prompt="Did the assistant solve the user's issue accurately?",
    ),
)

run = client.runs.create(dataset=dataset, name="support-router", recipe=recipe).wait()

print(run.artifact.id)
print(run.eval_report["pareto_summary"])
```

### When to use a router vs. fine-tuning vs. distillation

- **Start with a router (`RouterRecipe`)** when a cheap model already handles most of your requests well and you only need a frontier model for the hard ones. It's the fastest way to cut LLM spend without training a new generator.
- **Use [Supervised fine-tuning (SFT)](/docs/training/recipes/sft/) or [distillation](/docs/training/recipes/distillation/)** when no cheap model is good enough on its own yet and you want to teach a small model to handle the task directly.
- **Combine them** once you have a fine-tuned 8B model by putting it alongside a frontier model in your router.

### Parameters you might change

- **`models`:** the candidate models to route between. If your dataset only contains logs from one model, Gradiated replays your prompts against the others automatically. If your logs already include multiple models in `metadata.model`, you can leave `models` out.
- **`rubric`:** how quality is measured, the same parameter every recipe and eval uses. Pass a [`Judge`](/docs/training/rubrics/) with a prompt if your logs don't have scores yet, a `Rubric` with code checks, an existing score name (`"task_success"`), or a function.
- **`max_quality_drop`:** how much quality you'll trade for cost savings compared with your best model (`0.02`, or 2%, by default). The router is trained to route at this operating point.

Every other setting, including the router backbone, the eval split and custom pricing, has a default; see the [training parameters reference](/docs/reference/training-parameters/#routerrecipe).

## Read the evaluation report

Before deploying, check `run.eval_report`:

```json
{
  "eval_examples": 480,
  "fallback_model": "{{OPUS_MODEL}}",
  "fallback_quality": 0.912,
  "pareto_summary": {
    "target_max_drop": 0.02,
    "routed_quality": 0.904,
    "quality_drop": 0.008,
    "quality_drop_ci95": [-0.004, 0.019],
    "offload_rate": 0.64,
    "cost_savings_pct": 0.57,
    "ece": 0.018
  }
}
```

- **`cost_savings_pct`:** how much less you'll spend compared to sending every request to your fallback model while staying within `max_quality_drop`.
- **`quality_drop` and `quality_drop_ci95`:** the estimated quality difference vs. your fallback model, plus a low-to-high range showing how sure we are. Look at the high end of that range: if it's larger than the drop you're okay with, add more examples to your dataset before shipping.
- **`ece`:** how closely the router's predicted success rates match what actually happened on held-out examples (aim for under `0.05`).

## Deploy the router

Deploy your trained [`Artifact`](/docs/training/artifacts/) to Gradiated Cloud in one line with a `fallback` model:

<DocsCodeTabs>
  <DocsCodeTab label="Python">

```python
from grad import Grad

client = Grad()

# Host under your-org/support-router on Gradiated Cloud
run.deploy(fallback="{{OPUS_MODEL}}")

messages = [{"role": "user", "content": "Where is invoice #9941?"}]
tools = []  # the tool definitions you send with the request, if any

# Call directly if you dispatch to your own LLM providers:
decision = client.route("support-router", messages=messages, tools=tools)
print(decision.model)  # e.g. "qwen/qwen3-8b"; call it with your own provider client

# Later, once you know whether the ticket was resolved:
ticket_resolved = True
decision.record_feedback(score=1.0 if ticket_resolved else 0.0)
```

  </DocsCodeTab>
  <DocsCodeTab label="TypeScript">

```ts
import { Grad } from "@gradiated/grad";

const grad = new Grad();

await run.deploy({ fallback: "{{OPUS_MODEL}}" });

const messages = [
  { role: "user" as const, content: "Where is invoice #9941?" },
];
const tools: unknown[] = [];

const decision = await grad.route("support-router", { messages, tools });
console.log(decision.model); // call it with your own provider client

// Later, once you know whether the ticket was resolved:
const ticketResolved = true;
await decision.recordFeedback({ score: ticketResolved ? 1.0 : 0.0 });
```

As feedback comes in, Gradiated tracks live quality against the `max_quality_drop` target the router was trained for and stores it for your next retrain.

If you already call models through Gradiated with the [OpenAI SDK](/docs/openai-sdk/) or [Anthropic SDK](/docs/anthropic-sdk/), you can skip `client.route(...)` and pass `"model": "your-org/support-router"` directly to your chat completion call. See [Deploying](/docs/training/deploying/) for updates, rollbacks, and self-hosting options.
