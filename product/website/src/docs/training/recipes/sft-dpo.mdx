# Fine-tuning and preferences (SFT & DPO)

<DocsLead>Fine-tune an open model on gold outputs with SFT, align it against failure modes with DPO, and deploy with automatic syntax fallback.</DocsLead>

Use `sft` when you have verified examples of the exact output you want (fast code diff-merging, structured JSON extraction, SQL generation, or domain-specific formatting). Follow it with `dpo` when the model already knows the format but still makes avoidable mistakes you can pair as `chosen` vs. `rejected`.

## What data you need

### For SFT

- **Minimum volume:** 300–1,000 clean `(input, expected_output)` [trajectories](/docs/training/trajectories/) for narrow format or code-edit tasks; 2,000+ for broader tasks.
- **Data quality beats volume:** Filter out low-scoring or unverified traces with `filter` rather than training on raw logs.

```json
{
  "schema": "grad.trajectory/1",
  "session_id": "pr_481",
  "input": {
    "messages": [
      { "role": "system", "content": "Apply the edit snippet to the original file. Return only the merged file." },
      { "role": "user", "content": "<original>...</original>\n<edit>...</edit>" }
    ]
  },
  "expected_output": { "content": "export const retry = ..." },
  "scores": { "tests_passed": 1.0 }
}
```

### For DPO

Store pairs sharing the same `group_id` with `role: "chosen"` and `role: "rejected"`. Pairs stay together in the same train or eval split automatically.

```json
[
  {
    "schema": "grad.trajectory/1",
    "group_id": "pair_19",
    "role": "chosen",
    "input": { "messages": [{ "role": "user", "content": "Merge this diff." }] },
    "output": { "turns": [{ "role": "assistant", "content": "clean merged code..." }] }
  },
  {
    "schema": "grad.trajectory/1",
    "group_id": "pair_19",
    "role": "rejected",
    "input": { "messages": [{ "role": "user", "content": "Merge this diff." }] },
    "output": { "turns": [{ "role": "assistant", "content": "truncated code with syntax error..." }] }
  }
]
```

## Stage 1: Supervised fine-tuning (`sft`)

Train a LoRA adapter on GPU, filter to verified passing examples, split by `session_id`, and optionally merge the adapter into standalone weights on export.

<DocsCodeTabs action={<DocsApiKeyAction />}>
  <DocsCodeTab label="Python">

```python
from grad import Grad

client = Grad()

sft = client.runs.create(
    dataset="diff-merge-prod",
    name="fast-diff-merge",
    recipe="sft",
    base="Qwen/Qwen3-8B",
    adapter={"kind": "lora", "rank": 32},
    compute="gpu",
    optimizer={"kind": "adamw", "lr": 2e-4},
    split={"strategy": "by_session", "eval_fraction": 0.10},
    filter={"min_score": {"tests_passed": 1.0}},
    merge_adapter=True,
).wait(
    on_metric=lambda m: print(f"step={m.step} loss={m.loss:.4f}"),
)

print(sft.artifact_id)
```

## Stage 2: Preference alignment (`dpo`)

Pass `init_from=sft.artifact_id` to warm-start from the SFT checkpoint. You do not need to repeat `base`; the artifact manifest already carries it.

```python
dpo = client.runs.create(
    dataset="diff-merge-preferences",
    name="fast-diff-merge",
    recipe="dpo",
    init_from=sft.artifact_id,
    adapter="lora",
    compute="gpu",
    loss={"kind": "dpo", "beta": 0.1},
    optimizer={"kind": "adamw", "lr": 5e-5},
    merge_adapter=True,
).wait()

print(dpo.artifact_id, dpo.eval_report)
```

### Key parameters

| Field | Guidance |
| --- | --- |
| `adapter.rank` | `16`–`32` works for most single-task fine-tunes; increase to `64` for large coding or multi-skill datasets. |
| `optimizer.lr` | Start around `2e-4` for LoRA SFT and `2e-5`–`5e-5` for DPO. |
| `loss.beta` *(DPO)* | Higher `beta` (`0.2`–`0.5`) stays closer to the SFT reference; lower (`0.05`–`0.1`) pushes harder away from rejected patterns. |
| `merge_adapter` | Set `true` for lowest serving latency; leave `false` to hot-swap many adapters on one shared base model. |

## Deploy with syntax fallback

For structured JSON, SQL, or code-editing [endpoints](/docs/training/endpoints/), use `syntax_fallback`. If the fine-tuned model ever emits invalid syntax or fails your JSON schema, the endpoint retries automatically against a larger fallback model.

<DocsCodeTabs>
  <DocsCodeTab label="Python">

```python
from grad import Grad

client = Grad()

client.endpoints.create(
    slug="fast-diff-merge",
    artifact="fast-diff-merge@2026-11-25-2",
    capture_dataset="diff-merge-prod",
    strategy={
        "kind": "syntax_fallback",
        "validator": "typescript_ast",
        "fallback": "Qwen/Qwen3-32B",
    },
)

merged = client.endpoint("fast-diff-merge").infer(input={"original": original, "edit": edit})

client.feedback.record(
    inference_id=merged.inference_id,
    score=1.0 if tests_passed else 0.0,
    expected_output={"merged_code": human_fix} if human_fix else None,
)
```

  </DocsCodeTab>
  <DocsCodeTab label="TypeScript">

```ts
import { Grad } from "@gradiated/grad";

const grad = new Grad();

await grad.endpoints.create({
  slug: "fast-diff-merge",
  artifact: "fast-diff-merge@2026-11-25-2",
  captureDataset: "diff-merge-prod",
  strategy: {
    kind: "syntax_fallback",
    validator: "typescript_ast",
    fallback: "Qwen/Qwen3-32B",
  },
});

const merged = await grad
  .endpoint("fast-diff-merge")
  .infer<{ original: string; edit: string }, { mergedCode: string }>({
    input: { original, edit },
  });

await grad.feedback.record({
  inferenceId: merged.inferenceId,
  score: testsPassed ? 1.0 : 0.0,
  expectedOutput: humanFix ? { merged_code: humanFix } : undefined,
});
```

<DocsCallout label="Turn production misses into your next DPO dataset" tone="tip">
Whenever a developer fixes a bad output or `syntax_fallback` catches invalid JSON/AST, attaching `expected_output` via `feedback.record()` logs both the rejected attempt and the gold fix on the same trajectory — giving you ready-made SFT examples and DPO pairs with zero manual curation.
</DocsCallout>
