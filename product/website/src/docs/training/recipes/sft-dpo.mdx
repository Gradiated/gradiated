# Fine-tuning and preferences (SFT & DPO)

<DocsLead>Fine-tune an open model on gold outputs with SFT, align it against failure modes with DPO, and deploy with automatic syntax fallback.</DocsLead>

Use `SFTRecipe` when you have verified examples of the exact output you want (fast code diff-merging, structured JSON extraction, SQL generation, or domain-specific formatting). Follow it with `DPORecipe` when the model already knows the format but still makes avoidable mistakes you can pair as `chosen` vs. `rejected`.

## What data you need

### For SFT

- **Minimum volume:** 300–1,000 clean `(input, expected_output)` [trajectories](/docs/training/trajectories/) for narrow format or code-edit tasks; 2,000+ for broader tasks.
- **Data quality beats volume:** Filter out low-scoring or unverified traces on the `Dataset` (`dataset.filter(filters.MinScore(...))`) rather than training on raw logs.

```json
{
  "schema": "grad.trajectory/1",
  "session_id": "pr_481",
  "input": {
    "messages": [
      { "role": "system", "content": "Apply the edit snippet to the original file. Return only the merged file." },
      { "role": "user", "content": "<original>...</original>\n<edit>...</edit>" }
    ]
  },
  "expected_output": { "content": "export const retry = ..." },
  "scores": { "tests_passed": 1.0 }
}
```

### For DPO

Store pairs sharing the same `group_id` with `role: "chosen"` and `role: "rejected"`. Pairs stay together in the same train or eval split automatically.

```json
[
  {
    "schema": "grad.trajectory/1",
    "group_id": "pair_19",
    "role": "chosen",
    "input": { "messages": [{ "role": "user", "content": "Merge this diff." }] },
    "output": { "turns": [{ "role": "assistant", "content": "clean merged code..." }] }
  },
  {
    "schema": "grad.trajectory/1",
    "group_id": "pair_19",
    "role": "rejected",
    "input": { "messages": [{ "role": "user", "content": "Merge this diff." }] },
    "output": { "turns": [{ "role": "assistant", "content": "truncated code with syntax error..." }] }
  }
]
```

## Stage 1: Supervised fine-tuning (`SFTRecipe`)

Train a LoRA adapter, filter to verified passing examples, split by `session_id`, and optionally merge the adapter into standalone weights on export.

<DocsCodeTabs action={<DocsApiKeyAction />}>
  <DocsCodeTab label="Python">

```python
from grad import Grad, Model, adapters, filters, optim, splits
from grad.recipes import SFTRecipe

client = Grad()
dataset = client.datasets.get("diff-merge-prod").filter(
    filters.MinScore(tests_passed=1.0),
)

sft_recipe = SFTRecipe(
    model=Model("Qwen/Qwen3-8B"),
    adapter=adapters.LoRA(rank=32, merge_on_export=True),
    optimizer=optim.AdamW(lr=2e-4),
    split=splits.BySession(eval_fraction=0.10),
)

sft = client.runs.create(
    dataset=dataset,
    name="fast-diff-merge",
    recipe=sft_recipe,
).wait(
    on_metric=lambda m: print(f"step={m.step} loss={m.loss:.4f}"),
)

print(sft.artifact.id)
```

  </DocsCodeTab>

```ts
      split: splits.bySession({ evalFraction: 0.1 }),
    }),
  })
  .wait();

console.log(sft.artifact.id);
```

## Stage 2: Preference alignment (`DPORecipe`)

Pass `sft.artifact` directly as `model=` to warm-start from the SFT checkpoint (before or after `.wait()`), or use `.then(...)` as shorthand to queue Stage 2 behind Stage 1 on the server:

<DocsCodeTabs>
  <DocsCodeTab label="Pass sft.artifact (inspect or queue)">

```python
from grad import adapters, losses, optim
from grad.recipes import DPORecipe

prefs = client.datasets.get("diff-merge-preferences")

# Works whether `sft` already finished (after `.wait()`) or is still running (queues server-side).
dpo = client.runs.create(
    dataset=prefs,
    name="fast-diff-merge",
    recipe=DPORecipe(
        model=sft.artifact,
        adapter=adapters.LoRA(rank=32, merge_on_export=True),
        loss=losses.DPO(beta=0.1),
        optimizer=optim.AdamW(lr=5e-5),
    ),
).wait()

print(dpo.artifact.id, dpo.eval_report)
```

  </DocsCodeTab>
  <DocsCodeTab label="Fluent chaining (.then)">

```python
from grad import Model, adapters, filters, losses, optim, splits
from grad.recipes import DPORecipe, SFTRecipe

sft_ds = client.datasets.get("diff-merge-prod").filter(filters.MinScore(tests_passed=1.0))
prefs_ds = client.datasets.get("diff-merge-preferences")

dpo = (
    client.runs.create(
        dataset=sft_ds,
        name="fast-diff-merge",
        recipe=SFTRecipe(
            model=Model("Qwen/Qwen3-8B"),
            adapter=adapters.LoRA(rank=32),
            optimizer=optim.AdamW(lr=2e-4),
            split=splits.BySession(0.10),
        ),
    )
    .then(
        dataset=prefs_ds,
        recipe=DPORecipe(
            adapter=adapters.LoRA(rank=32, merge_on_export=True),
            loss=losses.DPO(beta=0.1),
            optimizer=optim.AdamW(lr=5e-5),
        ),
    )
    .wait()
)
```

  </DocsCodeTab>
</DocsCodeTabs>

### Key parameters

| Component | Guidance |
| --- | --- |
| `adapters.LoRA(rank=..., merge_on_export=...)` | `rank=16`–`32` works for most single-task fine-tunes (`64` for large coding datasets). Set `merge_on_export=True` for lowest serving latency, or leave `False` to hot-swap adapters on one shared base model. |
| `optim.AdamW(lr=...)` | Start around `2e-4` for LoRA SFT and `2e-5`–`5e-5` for DPO. |
| `losses.DPO(beta=...)` | Higher `beta` (`0.2`–`0.5`) stays closer to the SFT reference; lower (`0.05`–`0.1`) pushes harder away from rejected patterns. |

## Deploy with syntax fallback

For structured JSON, SQL, or code-editing [endpoints](/docs/training/endpoints/), use `strategies.SyntaxFallback` with any built-in `validators.*` class (`validators.TypeScriptAST()`, `validators.JSONSchema(...)`, `validators.SQL()`) or your own `Validator` subclass / callable. If the fine-tuned model emits invalid syntax, the endpoint retries automatically against a larger fallback model.

<DocsCodeTabs>
  <DocsCodeTab label="Python">

```python
from grad import Grad, Model, strategies, validators

client = Grad()
capture = client.datasets.get("diff-merge-prod")

endpoint = client.endpoints.create(
    slug="fast-diff-merge",
    artifact=dpo.artifact,
    capture_dataset=capture,
    strategy=strategies.SyntaxFallback(
        validator=validators.TypeScriptAST(),
        fallback=Model("Qwen/Qwen3-32B"),
    ),
)

merged = endpoint.infer(payload={"original": original, "edit": edit})

merged.record_feedback(
    score=1.0 if tests_passed else 0.0,
    expected_output={"merged_code": human_fix} if human_fix else None,
)
```

  </DocsCodeTab>
  <DocsCodeTab label="TypeScript">

```ts
import { Grad, Model, strategies, validators } from "@gradiated/grad";

const grad = new Grad();
const capture = await grad.datasets.get("diff-merge-prod");

const endpoint = await grad.endpoints.create({
  slug: "fast-diff-merge",
  artifact: dpo.artifact,
  captureDataset: capture,
  strategy: strategies.syntaxFallback({
    validator: validators.typeScriptAST(),
    fallback: new Model("Qwen/Qwen3-32B"),
  }),
});

const merged = await endpoint.infer<{ mergedCode: string }>({
  payload: { original, edit },
});

await merged.recordFeedback({
  score: testsPassed ? 1.0 : 0.0,
  expectedOutput: humanFix ? { merged_code: humanFix } : undefined,
});
```

<DocsCallout label="Turn production misses into your next DPO dataset" tone="tip">
Whenever a developer fixes a bad output or `SyntaxFallback` catches invalid JSON/AST, attaching `expected_output` via `feedback.record()` logs both the rejected attempt and the gold fix on the same trajectory — giving you ready-made SFT examples and DPO pairs with zero manual curation.
</DocsCallout>

## Going deeper with custom losses & loops

Swap `losses.DPO()` for a `losses.CustomLoss` subclass (such as `SimPOLoss`, `ORPOLoss`, or `KTOLoss`) right inside `DPORecipe`, or drop to [custom loops](/docs/training/custom-loops/) for differential LoRA+ learning rates (`optim.ParamGroup`) and zero-train-token weight merging (`client.artifacts.merge`).
