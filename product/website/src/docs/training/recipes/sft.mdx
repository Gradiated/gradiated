# Supervised fine-tuning (SFT)

<DocsLead>Fine-tune an open model on examples of the exact outputs you want.</DocsLead>

Use **`SFTRecipe`** when you have good examples of what the model should produce (code edits, structured JSON, SQL queries, or a specific style). Once it reliably follows your format, you can run [Preference tuning (DPO)](/docs/training/recipes/dpo/) or [RL for agents](/docs/training/recipes/rl-agents/) on top of the saved [`Artifact`](/docs/training/artifacts/) to improve it further.

## What data you need

- **Minimum volume:** 300–1,000 clean `(input, expected_output)` [trajectories](/docs/training/trajectories/) for focused tasks; 2,000+ for broader ones.
- **Quality beats volume:** don't train on raw, unfiltered logs. Score your dataset with a [`Judge`](/docs/training/rubrics/) and keep only high-scoring answers (or filter on an existing score like `tests_passed` if you already log one).

```json
{
  "schema": "grad.trajectory/1",
  "session_id": "pr_481",
  "input": {
    "messages": [
      { "role": "system", "content": "Apply the edit snippet to the original file. Return only the merged file." },
      { "role": "user", "content": "<original>...</original>\n<edit>...</edit>" }
    ]
  },
  "expected_output": { "content": "export const retry = ..." }
}
```

## Train with `SFTRecipe`

Score your `Dataset` once with a [`Judge`](/docs/training/rubrics/) to keep only good examples, train a LoRA adapter (`merge_on_export=True` merges the adapter into standalone weights for lowest serving latency), and split by `session_id` so multi-turn conversations never leak into eval:

<DocsCodeTabs action={<DocsApiKeyAction />}>
  <DocsCodeTab label="Python">

```python
from grad import Grad, Judge, Model, adapters, optim, splits
from grad.recipes import SFTRecipe

client = Grad()
dataset = client.datasets.get("diff-merge-prod")

# Score logs once with a Judge and keep only high-quality examples
judge = Judge(
    name="clean_merge",
    model=Model("claude-sonnet-4-6"),
    prompt="Did the assistant apply the edit accurately without breaking surrounding code?",
)
clean_dataset = dataset.score(judge).wait().filter(
    lambda t: t.scores["clean_merge"] >= 0.8,
)

sft_recipe = SFTRecipe(
    model=Model("Qwen/Qwen3-8B"),
    adapter=adapters.LoRA(rank=32, merge_on_export=True),
    optimizer=optim.AdamW(lr=2e-4),
    split=splits.BySession(eval_fraction=0.10),
)

sft = client.runs.create(
    dataset=clean_dataset,
    name="fast-diff-merge",
    recipe=sft_recipe,
).wait(
    on_metric=lambda m: print(f"step={m.step} loss={m.loss:.4f}"),
)

print(sft.artifact.id)
```

  <DocsCodeTab label="TypeScript">

```ts
import { Grad, Judge, Model, adapters, optim, recipes, splits } from "@gradiated/grad";

const grad = new Grad();
const dataset = await grad.datasets.get("diff-merge-prod");

const judge = new Judge({
  name: "clean_merge",
  model: new Model("claude-sonnet-4-6"),
  prompt: "Did the assistant apply the edit accurately without breaking surrounding code?",
});
const cleanDataset = (await dataset.score(judge).wait()).filter(
  (t) => t.scores.clean_merge >= 0.8,
);

const sft = await grad.runs
  .create({
    dataset: cleanDataset,
    name: "fast-diff-merge",
    recipe: recipes.sft({
      model: new Model("Qwen/Qwen3-8B"),
      adapter: adapters.lora({ rank: 32, mergeOnExport: true }),
      optimizer: optim.adamW({ lr: 2e-4 }),
      split: splits.bySession({ evalFraction: 0.1 }),
    }),
  })
  .wait();

console.log(sft.artifact.id);
```

If your logs already include a deterministic score (like `tests_passed` from CI), skip `dataset.score(judge)` and filter directly: `dataset.filter(lambda t: t.scores.get("tests_passed") == 1.0)`.

### When to use what

- **`adapters.LoRA(rank=16..32)`** *(default)* — best starting point for almost every task. Trains fast and generalizes well on 300–5,000 examples.
  - Set `merge_on_export=True` when you want lowest serving latency on a single dedicated model.
  - Leave `merge_on_export=False` when you want to serve many fine-tuned adapters on one shared base model.
- **`adapters.Full()`** — trains every weight in the model. Only worth it once you have 10,000+ examples and LoRA stops improving.
- **`splits.BySession(0.10)`** — keeps all turns from the same conversation together so eval scores aren't inflated by leakage.

## Deploy with a syntax fallback

For JSON, SQL, or code [endpoints](/docs/training/endpoints/), pair your trained [`Artifact`](/docs/training/artifacts/) with `strategies.SyntaxFallback` and a validator (`validators.TypeScriptAST()`, `validators.JSONSchema(...)`, `validators.SQL()`, or your own Python function). If the fine-tuned model outputs broken syntax, the endpoint automatically retries on a stronger fallback model:

<DocsCodeTabs>
  <DocsCodeTab label="Python">

```python
from grad import Grad, Model, strategies, validators

client = Grad()
capture = client.datasets.get("diff-merge-prod")

endpoint = client.endpoints.create(
    slug="fast-diff-merge",
    artifact=sft.artifact,
    capture_dataset=capture,
    strategy=strategies.SyntaxFallback(
        validator=validators.TypeScriptAST(),
        fallback=Model("Qwen/Qwen3-32B"),
    ),
)

merged = endpoint.infer(payload={"original": original, "edit": edit})

merged.record_feedback(
    score=1.0 if tests_passed else 0.0,
    expected_output={"merged_code": human_fix} if human_fix else None,
)
```

  </DocsCodeTab>
  <DocsCodeTab label="TypeScript">

```ts
import { Grad, Model, strategies, validators } from "@gradiated/grad";

const grad = new Grad();
const capture = await grad.datasets.get("diff-merge-prod");

const endpoint = await grad.endpoints.create({
  slug: "fast-diff-merge",
  artifact: sft.artifact,
  captureDataset: capture,
  strategy: strategies.syntaxFallback({
    validator: validators.typeScriptAST(),
    fallback: new Model("Qwen/Qwen3-32B"),
  }),
});

const merged = await endpoint.infer<{ mergedCode: string }>({
  payload: { original, edit },
});

await merged.recordFeedback({
  score: testsPassed ? 1.0 : 0.0,
  expectedOutput: humanFix ? { merged_code: humanFix } : undefined,
});
```

<DocsCallout label="Turn production misses into your next dataset" tone="tip">
When a developer fixes a bad answer or `SyntaxFallback` catches invalid JSON or code, calling `record_feedback(..., expected_output=...)` saves both the failed attempt and the fix on the same trajectory — giving you ready-to-use data for your next SFT or [DPO](/docs/training/recipes/dpo/) run.
</DocsCallout>
