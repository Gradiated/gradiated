# Tuning & troubleshooting

<DocsLead>
  How recipe defaults are chosen, when to change them, how to check chat
  templates before you pay, and how to fix common SFT and DPO failure modes.
</DocsLead>

The built-in [recipes](/docs/training/recipes/) resolve every hyperparameter for your base model and dataset, so your first run rarely needs tuning. `runs.plan()` and `--dry-run` print each resolved value. Use this page when you want to push quality further, watch a run closely, or diagnose a run that isn't converging. For every parameter and its default in one place, see the [training parameters reference](/docs/reference/training-parameters/).

## Learning rate

Every recipe defaults to `lr="auto"`. The resolved value depends on the base model, the recipe and the batch size, and it's printed in the dry run:

```text
Optimizer   AdamW(lr=5.00e-04, betas=(0.9, 0.95), grad_clip=1.0) · auto@2: calibrated for qwen/qwen3-8b at batch 128, sqrt batch scaling
```

Resolved values at the default batch size of 128, for each recipe's default model and adapter. Always read the dry run for your exact setup:

| Recipe                 | Default model            | `lr`   | Notes                                                                                              |
| ---------------------- | ------------------------ | ------ | -------------------------------------------------------------------------------------------------- |
| **SFT** (LoRA)         | `qwen/qwen3-8b`          | `5e-4` |                                                                                                    |
| **DPO**                | `qwen/qwen3-8b`          | `2e-5` | With `losses.DPO(beta=0.1)`. Much lower than SFT, so the model keeps the formatting SFT taught it. |
| **Model routers**      | `qwen/qwen3-0.6b`        | `5e-4` |                                                                                                    |
| **Decision models**    | `gradiated/linden-1`     | `3e-4` |                                                                                                    |
| **Context Cartridges** | `qwen/qwen3-8b`          | `1e-2` | Prefix KV tokens need a far higher LR than LoRA weights.                                           |
| **Embeddings**         | `baai/bge-small-en-v1.5` | `2e-5` | Small encoders train fast end-to-end with a low LR.                                                |

Rules of thumb behind `"auto"`:

- **Batch size:** the learning rate scales with the square root of the batch size. Doubling `batch_size` raises the resolved `lr` by about 1.4x.
- **Model size:** smaller models in a family want a higher learning rate than larger ones (SFT on `qwen/qwen3-0.6b` resolves to `8e-4`, on `qwen/qwen3-32b` to `3e-4`).
- **Rank:** `alpha` defaults to `32` for every rank, so the right learning rate stays the same when you change `rank`.
- **Objective:** as a sanity check, DPO runs at about 0.04x the SFT learning rate.

### What `"auto"` assumes

`"auto"` isn't a formula applied to any model. It's a table we calibrate with a learning-rate sweep on each base model before that model leaves preview. Each entry was measured at `batch_size=128`, `LoRA(rank=32, alpha=32)`, linear decay with 3% warmup and `AdamW(betas=(0.9, 0.95))`. When you change the batch size, the resolved value is scaled from that measured point by the square-root rule above:

```text
Optimizer   AdamW(lr=7.07e-04, betas=(0.9, 0.95), grad_clip=1.0) · auto@2: calibrated for qwen/qwen3-8b at batch 128, sqrt batch scaling
```

A model supports only the recipes it has a calibrated entry for. Any other pairing fails `runs.plan()` with `recipe_not_supported_for_model`, which lists the models that do support the recipe. On a [self-hosted](/docs/training/self-hosting/) server, register a custom checkpoint with `GRAD_EXTRA_MODELS_JSON` and give it a calibrated `lr` per recipe. Use the values above as a starting point, and sweep.

### Sweeping around the default

If you want to tune, sweep a small grid around the resolved value instead of guessing a number. `lr_scale` multiplies whatever `"auto"` resolves to, so the same sweep works for any model:

```python
from grad import Grad
from grad.recipes import SFTRecipe

client = Grad()
dataset = client.datasets.get("support-sft")

runs = [
    client.runs.create(
        dataset=dataset,
        name=f"support-sft-lr{scale}",
        recipe=SFTRecipe(model="qwen/qwen3-8b", lr_scale=scale),
    )
    for scale in (0.5, 1.0, 2.0)
]
for run in runs:
    run.wait()
    print(run.name, run.eval_report.eval_loss)
```

Keep the best one, then sweep again around it only if the best was at the edge of the grid.

## LoRA rank

The default is `adapters.LoRA(rank=32)`. Rank has little effect on cost, so you rarely need to go lower.

- **Small datasets** (under ~5k records): ranks of `8`–`16` learn as well as `32`.
- **SFT on large datasets** (over ~50k records): try `64`–`128`. Low ranks can underfit on broad, high-volume tasks.

## Batch size and number of steps

Every recipe defaults to `batch_size=128` for `epochs=1`. Defaults for every recipe are in the [reference](/docs/reference/training-parameters/#optimization).

The plan warns when a run will take fewer than 100 optimizer steps, because short runs end before the learning rate schedule does its job. Fix it with a smaller batch, more epochs, or more data:

```text
  ! 84 steps is below the 100 we recommend; use batch_size=107 or more epochs/data.
```

More than 2–3 epochs over the same SFT data usually overfits. Prefer more data, or a smaller batch for more steps.

## Chat templates and loss masks

Gradiated renders chat templates with the base model's pinned tokenizer, so you never hand-build tokens or special tokens. Three options control what gets trained:

- **`thinking="auto" | "on" | "off"`:** `"auto"` keeps the base model's default. For Qwen3, thinking is on, and assistant turns without a `<think>` block train with thinking off so the model learns to answer directly. There are no effort levels (`"low"`, `"high"`): the Qwen3 chat template only switches thinking on or off.
- **`preserve_thinking=False`:** whether earlier assistant turns keep their reasoning in the prompt. Most chat templates strip it, which is the default. Set `True` for agents that rely on reasoning from previous turns.
- **`train_on="last" | "all_assistant"`:** `"last"` (the default for chat records) trains only the final assistant turn. Use `"all_assistant"` for multi-turn agent traces. Tool outputs and user turns are never trained.

These settings are checked against your data rather than silently patched: a record whose target contains a `<think>` block when `thinking="off"`, or a target with no reasoning when `thinking="on"`, fails `runs.plan()` with the record ID.

### One template everywhere

Every run pins the template by ID and revision (for example `qwen3@3`), and the dry run prints it. The same pinned template, `thinking` and `preserve_thinking` values are stored on each checkpoint and used for evaluation and the deployed endpoint, so a model never trains with one prompt format and serves with another. Deployed reasoning models return their reasoning in `reasoning_content`, separate from `content`, matching the OpenAI-compatible convention.

We test each template revision so that generation prompts match the base model's Hugging Face chat template token for token. When a template has to change (for example to fix a tool-call format), it gets a new revision. Existing runs and checkpoints keep the revision they were trained with, and the changelog lists the change.

Preview the rendering before paying for a run. Trained spans are marked, and the summary shows what fraction of each record is trained. Token counts in the preview are estimates (about 4 characters per token, reported as `token_counts: "estimated"`); exact counts come from the run's metrics:

## Checkpoints, resuming, and spend caps

Managed recipe runs checkpoint automatically every 10% of steps, and at least every 20 steps, including optimizer state. They evaluate on the held-out split at the same points (change it with `eval_every=`), and `run.artifact` is the best checkpoint by eval (`select="best"`; pass `select="last"` to keep the final one).

- **What's kept:** the checkpoint that becomes `run.artifact` and the final checkpoint never expire, and both are deployable and downloadable as PEFT weights with no conversion step. Intermediate checkpoints are kept for 30 days unless you promote one with `ckpt.promote(name=...)`. Change the default with `checkpoint_ttl_days=` on the recipe.
- **What each checkpoint records:** base model and revision, adapter config, chat template revision, `thinking` and `train_on`, the resolved `lr`, the resolved `loss` with its rule version, and the step. Evaluations and deploys read these, so you never pass them again.

Set `max_cost_usd=` on every run you start. When the cap is reached, the run stops gracefully, saves a checkpoint, and ends with status `stopped_budget`, so a mistake costs at most the cap. Resume a stopped, failed, or cancelled run from its latest checkpoint; a budget-stopped run needs a higher cap:

```python
from grad import Grad
from grad.recipes import SFTRecipe

client = Grad()
run = client.runs.create(
    dataset=client.datasets.get("support-sft"),
    name="support-sft",
    recipe=SFTRecipe(model="qwen/qwen3-8b"),
    max_cost_usd=20,
).wait()

if run.status == "stopped_budget":
    run.resume(max_cost_usd=40).wait()
```

From the CLI, use `grad runs resume RUN --max-cost-usd 40 --wait`.

A resumed or requeued run is billed only for the tokens it processes: the steps up to its checkpoint aren't billed again, and steps replayed after the last checkpoint are. `wait()` gives up after 24 hours by default (the run keeps going); pass `timeout=` to change that.

## Troubleshooting common failure modes

| Symptom                                                     | Likely cause                                                                                                                                       | What to do                                                                                                                                                              |
| ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **DPO outputs get repetitive or degenerate**                | `lr` is too high, `beta` is too low, or `chosen` / `rejected` pairs come from a very different model than the starting weights.                    | Keep `lr="auto"` (or try `lr_scale=0.5` if you set your own), increase `losses.DPO(beta=0.1..0.2)`, and generate pairs from the same SFT checkpoint you start DPO from. |
| **Answers cut off mid-sentence or mid-thought**             | SFT records were truncated at the training sequence limit, or the eval or serving `max_tokens` is too low.                                         | Check the plan's truncation warnings; shorten records, pick a model with a longer training sequence limit, or raise `max_tokens`.                                       |
| **Model ignores or garbles the chat format after training** | Training data didn't match the base model's template (for example, thinking blocks on some turns but not others), or the wrong turns were trained. | Run `grad render <dataset> --model <base>` and check which spans are trained; set `thinking=` and `train_on=` explicitly.                                               |
| **Eval score drops while train loss drops**                 | Overfitting on a small dataset or leakage between train and eval splits.                                                                           | Keep `epochs=1` (2 at most), keep `splits.BySession(eval_fraction=0.10)` and `select="best"`, or add more diverse examples.                                             |
