# Tuning & troubleshooting

<DocsLead>Practical defaults for learning rates, LoRA rank, W&amp;B / MLflow logging, crash recovery, and fixing common SFT, DPO, and RL failure modes.</DocsLead>

The built-in [recipes](/docs/training/recipes/) ship with tested defaults so you rarely need to tune hyperparameters on your first run. Use this page when you want to push quality further, hook up experiment tracking, or diagnose a run that isn't converging.

## Starting hyperparameters by task

| Task | Adapter | Typical learning rate | Practical rule of thumb |
| --- | --- | --- | --- |
| **SFT** | `adapters.LoRA(rank=8)` | `1e-4` to `2e-4` | Start with `rank=8`. Only bump to `16`–`32` if train loss stays high on a large, diverse dataset. |
| **DPO** | `adapters.LoRA(rank=8)` | `2e-5` to `5e-5` | Start from an SFT artifact; keep `beta` around `0.1`. |
| **RL (GRPO / CISPO)** | `adapters.LoRA(rank=8)` | `1e-5` to `3e-5` | Use `group_size=8`. Higher LR causes formatting collapse or KL spikes. |
| **Distillation** | `adapters.LoRA(rank=8)` | `5e-5` to `1e-4` | On-policy `TopKKLDistill(top_k=32)` usually beats off-policy text SFT. |
| **Context Cartridges** | `adapters.PrefixKV(num_tokens=256)` | `1e-2` to `2e-2` | Prefix KV tokens need a much higher LR than LoRA weights; try `512`–`1024` tokens for very large contexts (up to ~500k tokens). |
| **Embeddings** | `adapters.Full()` | `1e-5` to `3e-5` | Small encoders (~33M–300M) train fast with full weights and a low LR. |
| **Full fine-tuning (LLMs)** | `adapters.Full()` | `1e-5` to `3e-5` | Use ~10x lower LR than LoRA for the same model and batch size. |

## Experiment tracking (W&B and MLflow) & live samples

Scalar loss curves rarely tell the full story during RL or preference tuning. Attach a logger to stream metrics and sample completions to Weights & Biases or MLflow, or inspect live completions straight from the CLI:

<DocsCodeTabs>
  <DocsCodeTab label="Python (Recipes & Custom loops)">

```python
from grad import Grad, loggers
from grad.recipes import GRPORecipe

client = Grad()

run = client.runs.create(
    dataset=dataset,
    name="sql-agent",
    recipe=GRPORecipe(model=sft_art, rubric=rubric),
    loggers=[
        loggers.WandB(project="sql-agent-rl", tags=["qwen3-8b"]),
        # or loggers.MLflow(tracking_uri="https://mlflow.internal.example", experiment="sql-agent")
    ],
).wait()
```

  </DocsCodeTab>
  <DocsCodeTab label="CLI (Inspect live completions)">

```bash
# Stream loss, reward, and KL metrics
grad runs logs run_01J9Z4K --follow

# Print actual model completions and rubric scores from recent steps to spot reward hacking
grad runs logs run_01J9Z4K --samples 5
```

</DocsCodeTabs>

## Troubleshooting common failure modes

| Symptom | Likely cause | What to do |
| --- | --- | --- |
| **RL reward flatlines near `0.0`** | Prompts are too hard for the starting model, or binary `0/1` grading gives zero gradient whenever all 8 attempts fail. | Run a quick 200–500 example [SFT](/docs/training/recipes/sft/) warmup first, add partial-credit checks to your [`Rubric`](/docs/training/rubrics/) (e.g. valid syntax = `0.3`), or filter out impossible prompts. |
| **>70% of RL groups have identical scores** | Prompts are either trivially solved (`all 1.0`) or unsolvable (`all 0.0`). | Keep `skip_zero_var=True` and filter your dataset to medium-difficulty tasks (where the base model passes 15%–80% of the time). |
| **Broken JSON, SQL, or tool calls appear mid-RL** | Base model formatting wasn't solid before RL, or learning rate is too high. | Run short SFT first, lower `lr` to `1e-5`–`2e-5`, and add a deterministic validator (`validators.SQL()`, `validators.JSONSchema(...)`) to your `Rubric`. |
| **`kl_sample_train` spikes or reward collapses** | Weight updates are too large per step, or async rollout workers are several steps stale. | Cut `lr` in half, set `kl_beta=0.02`–`0.05`, or switch to `losses.CISPO` for asynchronous rollout pools. |
| **High rubric score, bad real answers (reward hacking)** | Model found a shortcut that fools an LLM `Judge` (such as verbose fluff or echoing prompt keywords). | Read live outputs with `grad runs logs <id> --samples 5`, tighten the `Judge` prompt with failure examples, and add deterministic code checks alongside the `Judge`. |
| **DPO outputs get repetitive or degenerate** | `lr` is too high, `beta` is too low, or `chosen` / `rejected` pairs come from a very different model than the starting weights. | Lower `lr` to `2e-5`, increase `losses.DPO(beta=0.1..0.2)`, and generate pairs from the same SFT checkpoint you start DPO from. |
| **Eval score drops while train loss drops** | Overfitting on a small dataset or leakage between train and eval splits. | Reduce epochs (1–2 epochs is usually plenty for SFT), keep `splits.BySession(eval_fraction=0.10)`, or add more diverse examples. |

## Custom loop session lifecycle & crash recovery

Managed `Recipe` runs run entirely on Gradiated's servers, so closing your laptop never interrupts them.

When driving your own [custom loop](/docs/training/custom-loops/) from a local machine or CI runner:

- **Session idle timeout:** an open `Trainer` session stays warm while receiving steps and closes automatically after 30 minutes of inactivity (you are never billed while idle).
- **Checkpoint periodically:** call `trainer.save_state(name=f"step-{step}")` every 50–100 steps so both weights and optimizer moments are persisted durably.
- **Resume cleanly after any crash or network drop:** pass the saved checkpoint ID to `client.trainers.resume(ckpt)` to pick up at the exact same step and optimizer state without losing progress:

```python
from grad import Grad

client = Grad()

# Resume weights, optimizer moments, and step counter after a disconnect or CI retry
with client.trainers.resume("code-agent-step-200") as trainer:
    for step, batch in enumerate(remaining_batches, start=200):
        ...
        if step % 50 == 0:
            trainer.save_state(name=f"code-agent-step-{step}")
```
