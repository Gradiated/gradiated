# Runnable current control and background frontier

## Question

On one content-addressed, currently runnable GLM-4.7-Flash AWQ/vLLM/L40S stack, does cache-off c16 or c32 reduce sustainable dollars per output token by at least 5% versus an adjacent c8 control while preserving the required quality and completing reliably inside a declared background-job envelope?

## Why it matters

The retained V21 c8 result ($0.670/M output tokens at 355.772 output tok/s) is useful historical evidence, but it is not a reproducible campaign control. The frozen V21 tokenizer/runtime contract is internally inconsistent: the retained runtime reports Transformers 5.3.0.dev0 while the binding requires 5.12.1, and the available 5.12.1 path produces 164 rather than 183 tokens for all 24 amended prefix requests. V31 and V32 then spent a combined $0.813535908 without running a batching arm. Further V21 identity repair is not admissible.

The campaign still needs a direct intervention result. A fresh c8/c16/c32 ladder can establish a runnable current control and test the high-value background batching mechanism in one paid session. Cloudflare Workers AI's exact-model listing supplies a current vendor-reported price anchor of $0.88/M output-equivalent tokens at 8:1, but not a matched quality or service comparator.

## Relevant evidence

- V32 retained the actual transferred public-AWQ checkpoint/tokenizer bytes and current runtime observations before failing only against the historical V21 identity expectations.
- The durable Nebius L40S controller/watchdog canary passed create, two-view observation, deadline ownership, deletion, and zero final inventory.
- V21 measured 333,488 KV-cache tokens, making c16 plausible and c32 a useful memory/reliability falsifier, but V21 throughput and cost are non-transferable priors rather than the new denominator.
- The fixed campaign workload is 8,192 input tokens and up to 1,024 output tokens per request; latency is tradeable, but reliability, quality, and all-in cost are not.

## Scope

Complete preparation and measurement in one researcher turn; do not return another readiness-only handoff. Before provider creation, build a content-addressed manifest from the bytes that will actually run: checkpoint revision/files, tokenizer files and rendered token IDs, container/runtime and Python package identities, controller and runner, generation settings, and workload records. Starting from the campaign workload content, deterministically construct and retain 32 records that are exactly 8,192 tokens under that tokenizer, with a 1,024-token maximum output. This is a new workload identity. Do not assert or require any frozen V21 tokenizer hash, token count, runtime version, prompt digest, or direct comparability.

The same-turn zero-cost gates are: all local source/identity bindings pass; a fake external-controller run reaches a typed terminal artifact; provider inventory is empty; the selected L40S rate fits the cap; and the current endpoint has a proven route to retain the development-quality evidence below. A failed gate stops before create and is a scientific or operational falsifier, not an invitation to repair the historical identity.

If the gates pass, use exactly one Nebius L40S allocation under the proven independent systemd controller/watchdog boundary. Load the current public AWQ checkpoint once, keep checkpoint, tokenizer, runtime, scheduler budget, sampling, seed, prefix caching off, and server configuration fixed, then run adjacent cache-off c8, c16, and c32 arms from the same 32-record corpus. c8 is the new current control. Admit c32 only if the live allocator/KV check passes; an OOM or admission failure is itself the c32 result. Every admitted request must finish without truncation or semantic error within a 120-second arm deadline. TTFT, TPOT, queueing, and makespan are tradeoff measurements, not inherited interactive rejection gates.

Re-establish current development quality once in the resident session using the existing 36-case development packet and raw prompt/input-logprob evidence through a locally proven adapter to the actual endpoint; do not generate or inspect a holdout. Also retain deterministic decoded-output/semantic comparisons across batching arms. If the current endpoint cannot produce the bound evidence or the development screen fails, report the economics as ineligible rather than weakening the quality protocol.

Retain raw requests/responses, success and truncation state, token counts, throughput, TTFT/TPOT/queue/makespan, scheduler and KV state, VRAM, utilization, power/energy, server logs, quality scores, allocation exposure, setup/load/useful-GPU/teardown time, effective provider rate, storage/transfer/retry/orchestration costs, and terminal cleanup evidence. Report steady-state and duty-cycle-amortized dollars per million output tokens separately.

Do not enable prefix caching, modify kernels or weights, change representation/runtime between arms, repair V21, run an H100, open a second allocation, or overlap another provider mutation. This project is sole provider owner for at most $1.00 all-in and 3,600 seconds. Arm cleanup before creation and require absent instance and disk in both direct-resource and inventory views.
