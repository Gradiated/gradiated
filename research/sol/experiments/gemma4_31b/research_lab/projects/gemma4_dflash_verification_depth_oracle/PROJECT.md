# DFlash verification-depth oracle

## Question

Does the immutable accepted-prefix telemetry already retained from the exact
Gemma 4 DFlash work imply a materially cheaper request- or depth-adaptive
TARGET_VERIFY policy than fixed depth four, before spending on another
endpoint request?

## Why it matters

Lossless one-forward parallel drafting is one of the campaign's few mechanisms
with enough potential to contribute to the locked
`0.500119281574996 s/request` target. The last request-25 observer is
uninterpretable because it persisted only a response length and digest, but
that failure rejects the observer record rather than the drafting mechanism.
The registered warm-bench record separately states that accepted-prefix
telemetry is present. Its best use now is a zero-GPU oracle bound: if even an
oracle cannot save meaningful verification work while preserving accepted
tokens, another confidence controller is not competitive.

## Immediate experiment

Work offline and do not claim or contact a GPU. Starting from the exact
artifact references in `runtime/gpus.json` and the immutable DFlash project
terminals, locate the smallest accepted-prefix record that contains real,
distinct request/depth events. Hash the consumed bytes before analysis. Do not
use the unrecoverable request-25 response as if its raw bytes existed.

Build one reproducible event-level simulator for the exact c32, depth-four
verification geometry. Compare fixed depth four with an oracle that may stop
or shrink verification per request using only information available before
the avoided rows execute. Account for verified rows, accepted target tokens,
draft invocations, target-forward launches, padding, and request completion.
Translate the row and launch deltas into a conservative H200 service-time bound
using the retained exact-consumer measurements; do not transfer an unmatched
endpoint delta.

Return either:

1. `DFLASH_VERIFICATION_DEPTH_ORACLE_TERMINAL.json` with a positive physical
   ceiling, the smallest observable state needed by a realizable controller,
   and one source-level controller candidate; or
2. a typed `none` showing that the accepted-prefix distribution, missing
   pre-decision observables, or oracle ceiling cannot support a competitive
   follow-up.

This project must produce a measured oracle or typed falsification, not a
readiness packet, literature survey, request replay, or GPU launcher.

## Scope and resources

- Researcher profile: deep.
- Wall-clock budget: 50 minutes.
- GPU budget: zero; this project is GPU-ineligible.
- Provider spend: `$0`.
- Storage budget: 256 MiB under this project.
- Inputs: existing local immutable DFlash telemetry and exact-consumer
  terminals only.
- Quality label: analytical/oracle evidence, not a deployable model result.

## Portfolio consequence

A strong oracle ceiling keeps DFlash active and nominates one fresh,
content-addressed controller experiment after the direct H200 lane releases.
A weak ceiling or absent causal telemetry closes verification-depth adaptation
without making a claim about other one-forward drafting designs.
