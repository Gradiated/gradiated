# Upstream NGRAM runtime semantic rebase

## Question

Does one newer upstream SGLang runtime contain a source-level NGRAM,
tree-verification, cache/position, or Gemma hybrid-attention correction that
can remove the observed deterministic semantic divergences while preserving
the native depth-12 NGRAM economic path?

This is a full-stack runtime-replacement hypothesis, independent of the active
completed-request write-isolation intervention. It may not patch, reinterpret,
or replay that in-flight project.

## Why this matters

The pinned SGLang runtime at commit
`28b095c01005d4a3a2a5b637b7d028b07fba31b2` has demonstrated economically
promising native NGRAM execution. The valid support-two 791-request
discriminator completed with zero failures, zero queue, long unaffected
trunks, and `$0.1393159641142523/M`, but it diverged semantically at request
790. The repaired request-local candidate also diverged, at request 170, and
was much more expensive. These failures may reflect the pinned runtime's
target-verification realization rather than online-corpus admission policy.

A newer unmodified runtime is valuable only if its exact source path explains
why it could repair semantics and it retains the exact model, native NGRAM,
FP8, hybrid-attention, CUDA-graph, and workload capabilities needed for a
short matched endpoint test.

## Bound evidence

Use `DIRECTOR_BINDING.json`. Mechanically verify every referenced byte before
analysis. The comparator is the pinned digest image and commit in that file.
The support-two terminal is measured evidence; the request-local result in the
current bench handoff is corroborating evidence only.

Evidence labels:

- Support-two discriminator and economics: measured.
- Pinned source and workload identities: measured/content-addressed.
- Upstream commit claims before reproduction: source-derived or
  vendor-reported.
- Any projected endpoint benefit before GPU measurement: analytical.

## Scope and immediate experiment

1. Inspect current official SGLang source, releases, changelogs, and merged
   changes after the pinned commit. Trace the exact native NGRAM proposal,
   target verification, tree mask/retrieve mapping, accepted-token commit,
   request cleanup, cache position, Gemma local/global attention dispatch, and
   CUDA-graph geometry used by the bound workload.
2. Compare those paths with the pinned bound source and the measured
   support-two failure. Identify a concrete causal change capable of affecting
   the first divergent target-verification state. Generic "newer is better,"
   unrelated performance changes, and unresolved source drift are not
   candidates.
3. Select at most one immutable upstream commit or release. Freeze its commit,
   source diff, image/build recipe, exact model/runtime flags, and a smallest
   activation-plus-semantic discriminator. Prove from source that native
   Gemma 4 31B FP8, depth-12 NGRAM, hybrid local/global attention, tokenizer,
   and the required API remain supported.
4. Return either a content-addressed, execution-ready candidate packet or a
   typed `none`. Do not claim a GPU, build on the provider, load the model, or
   run any endpoint in this phase.

If a candidate is nominated, the later paid extension remains in this same
project. It must wait for the active priority-8500 owner to release the
retained H200, then run one smallest activation/semantic discriminator before
any 791-request economic sample. The director must separately authorize that
extension.

- No provider mutation, GPU claim, checkpoint transfer, image build on a paid

- No quality or economic transfer across runtime identities.
- Do not modify the active priority-8500 project, owner, claim, server, or
  artifacts.

## Decision gate

Nominate exactly one upstream runtime only if all of the following are true:

- a source-level causal change touches the observed semantic-risk path;
- the exact model and native depth-12 NGRAM/FP8/hybrid-attention features are
  supported;
- the candidate is content-addressed and reproducibly buildable;
- the smallest paid falsifier can run on the retained H200 after release
  within at most 45 claimed minutes and `$3`;
- the later endpoint retains exact normalized semantics, zero failures, peak
  queue at most 30, final queue zero, stable release timing, long unaffected
  trunks, and planning cost at or below `$0.14/M`.

Otherwise return typed `none`; do not substitute a second runtime.
