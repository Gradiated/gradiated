# L40S resource model for GLM-4.7 Flash

This is a working model of the current target chip, not a generic specification sheet. Researchers should update measured unknowns when they run a decision-bearing experiment. Official specifications are hardware facts; mappings to GLM and opportunities below are derived hypotheses until measured.

## Hardware facts

| Resource | L40S / Ada SM89 | Research consequence |
| --- | --- | --- |
| Parallel fabric | 142 SMs; 18,176 CUDA cores; 568 fourth-generation Tensor Cores, or 4 per SM | Small grids and fragmented per-expert matrices can leave much of the device idle even when aggregate GPU utilization is high. |
| SM residency | Up to 48 warps, 1,536 threads, and 24 blocks per SM; 64K 32-bit registers per SM; 255 registers per thread | Register-heavy attention or dequantization kernels can collapse occupancy. Block count alone is not enough; inspect registers, shared memory, eligible warps, and issue stalls. |
| L1/shared | 128 KB unified L1/texture/shared storage; selectable shared carveouts of 0/8/16/32/64/100 KB; 99 KB maximum shared memory per block after CUDA's reservation | More shared memory can improve data reuse but removes L1 and may reduce resident blocks. A tile that exceeds 99 KB is architecturally impossible regardless of idle device memory. |
| L2 | 96 MB on AD102; persistence controls are available | The 20.17 GB checkpoint is about 210 times L2 and cannot be cached as a model. Component/hot-set locality can still matter: one quantized expert or BF16 shared expert fits; a 634 MB BF16 output head does not. |
| Device memory | 48 GB GDDR6 ECC, 864 GB/s | Capacity and bandwidth are scarcer than on H100-class HBM. The measured serving footprint was 38,985 of 46,068 MiB, leaving about 6.9 GiB; c32 failed the existing memory bound. Model-state reductions can be valuable mainly when they unlock a larger batch or cheaper chip. |
| Tensor math | Dense peak: 362.05 TFLOP/s BF16/FP16 and 733 TFLOP/s FP8; structured sparsity doubles the published figures. Ada Tensor Cores support FP8. | A dense BF16 roofline crossover is roughly 419 FLOP/byte. Decode matrices at c16 are generally far below that unless weights are reused effectively, so peak Tensor FLOPS are not a throughput prediction. Confirm that the selected runtime actually emits the supported path. |
| Links/topology | PCIe Gen4 x16, 64 GB/s bidirectional; no NVLink; no MIG | Avoid expert/KV traffic across host PCIe in the steady decode path. If the model fits one GPU, data-parallel replicas are a stronger prior than PCIe tensor parallelism. The card cannot be partitioned with MIG. |
| Power | 350 W maximum | Power matters for owned-compute economics, but use measured board power and productive utilization rather than TDP for a final estimate. |

Primary sources: [NVIDIA L40S specifications](https://www.nvidia.com/en-eu/data-center/l40s/), [NVIDIA Ada tuning guide](https://docs.nvidia.com/cuda/ada-tuning-guide/index.html), and [NVIDIA Ada architecture whitepaper](https://images.nvidia.com/aem-dam/Solutions/geforce/ada/nvidia-ada-gpu-architecture.pdf).

## Exact GLM geometry mapped to L40S

- Hidden width 2,048 and MoE width 1,536 are clean multiples of 128. Q-LoRA rank 768, KV-LoRA rank 512, 256-dimensional QK and value heads, and vocabulary 154,880 are also divisible by 128. The obvious dense dimensions are already tensor-tile friendly; arbitrary width cuts can make kernels less efficient even while reducing FLOPs. Candidate widths/ranks should preserve useful tile multiples unless a measured kernel favors another shape.
- The model has 46 MoE layers, 64 routed experts per layer, top-4 routing, and one shared expert. At c16 there are only 64 routed token-expert assignments per layer. Under uniform routing that is one token row per expert, on average, spread across 142 SMs. This makes grouped-MoE fragmentation, routing/scatter overhead, tiny-M GEMM efficiency, and expert-load imbalance first-order hypotheses.
- A routed expert contains roughly 9.44 million uncompressed parameters across gate/up/down projections. At W4 its ideal packed weights are roughly 4.5 MiB before scales/metadata, small enough individually for L2; all 64 experts in a layer are roughly 288 MiB and do not fit. Batch-local grouping and expert popularity therefore matter more than whole-layer persistence.
- The BF16 shared expert sees every active token and has materially better M than a typical routed expert. Removing it saves work, but it is not necessarily the least efficient work. Conversely, reducing routed top-k can shrink already-small groups and lose kernel efficiency. Measure the resulting grouped-GEMM shapes rather than assuming work reduction transfers linearly.
- The untied BF16 output head is `[M,2048] x [2048,154880]`, with 634,388,480 weight bytes. At c16 an efficient GEMM can reuse each weight tile across 16 rows: the ideal lower-bound weight stream is about 634 MB per decode step, not per output token. At 535.286 output tok/s, that is about 21.2 GB/s if every step has 16 active rows; 339 GB/s is the no-cross-row-reuse upper bound. Its observed duration may therefore reflect small-M occupancy, launch shape, or cache behavior as well as DRAM bandwidth.
- MLA uses 20 heads, KV latent rank 512, and 256-dimensional values. The attempted `BLOCK_H=16`, `BLOCK_N=64`, two-stage grouped decode needed 159,744 bytes of shared memory and could not launch under the 101,376-byte block limit. The legal one-stage repair regressed endpoint throughput. Reducing latent/value geometry enough to admit a two-stage 64-token tile is a concrete model/chip co-design hypothesis.
- With BF16 KV and the checkpoint's 47 layers, a simple MLA state estimate of `(512 latent + 64 rope) * 2 bytes * 47` is about 52.9 KiB per cached token before allocator details. At 16 sequences and 8,192 input tokens this is about 6.6 GiB. Reducing the latent rank from 512 to 256 would analytically save about 2.9 GiB at that geometry; FP8 KV could approximately halve this state if the exact runtime path supports it. These are capacity estimates, not measured allocator savings.

## Highest-information co-design hypotheses

1. **Reduce fragmentation, not just top-k.** Compare the current 64-expert/top-4 geometry with execution proxies for fewer merged experts and jointly adjusted top-k. Fewer experts can increase rows per active expert, reduce routing metadata, improve SM filling, and reduce resident weights. Record the per-layer histogram of expert GEMM `M`, waves per 142 SMs, and grouped-kernel occupancy.
2. **Trade KV rank for a legal attention tile and c32.** Sweep exact-shape latent/value dimensions at tile-friendly multiples while recording shared bytes, registers, occupancy, kernel time, and estimated KV capacity. Promote dimensions that both make a faster two-stage tile legal and move the c32 memory boundary; this compounds a kernel benefit with batch reuse.
3. **Use Ada-native precision selectively.** The public AWQ checkpoint leaves layer 0, shared experts, and `lm_head` in BF16. Test exact-shape FP8 or supported structured-sparse proxies for those components. A representation is useful only if the runtime uses Ada Tensor Cores without expensive conversions and the saved memory/traffic transfers to wall time or batch capacity.
4. **Increase useful work per launch.** At c16, 142 SMs are difficult to fill with tiny expert groups and some small-M projections. Kernel fusion, persistent grouped scheduling, CUDA graphs, and architecture changes that combine or regularize work may beat nominally larger FLOP reductions that create smaller kernels.
5. **Exploit capacity discontinuities.** A few percent less state has little value if c16 remains optimal; enough less state to admit c32 or fit a cheaper 32 GB GPU can have a discontinuous economic payoff. Rank changes by the operating point they unlock.

## Minimal discriminating measurements

Do not profile the entire server by default. For the current top candidate, use an exact-shape kernel or a short marked serving region and collect only enough data to decide among limits:

- elapsed kernel and endpoint wall time, launch count, grid/block shape, active expert `M` distribution;
- achieved occupancy, active/eligible warps, registers per thread, shared bytes per block, and issue-stall reasons;
- Tensor Core utilization and instruction mix, including whether FP8/INT4/BF16 paths actually execute;
- L1/L2 hit rates, DRAM bytes and throughput, and arithmetic intensity;
- memory footprint/KV blocks, active batch rows, board power, and clocks.

Interpret changes causally. Lower DRAM bytes with unchanged wall time means another resource dominates. Lower nominal FLOPs with lower occupancy can regress. Higher cache hit rate is useful only if it shortens the critical path. Aggregate `nvidia-smi` utilization does not distinguish any of these.

## Current measured anchors and unresolved questions

- Measured c16 endpoint: 535.286 output tok/s, 98.36% mean GPU utilization, approximately $0.571/M output tokens at the shared $1.10/hour planning rate.
- The earlier attention specialization removed substantial traced attention work but improved endpoint throughput only 1.046%, so attention was not then the dominant serving critical path. A model change that also unlocks c32 is materially different and remains open.
- The current trace reports kernel-duration classes, but it does not yet provide the SM occupancy, register, cache, DRAM-byte, or Tensor Core counters needed to identify the L40S physical limiter. One bounded exact-shape/c16 profiling session should fill this gap while testing a scientific arm; it should not become another general observability project.
