# Durable provider-controller admission proof — research log

## 2026-07-15 — zero-provider external-controller proof passes

**Question.** Can a controller and independent watchdog survive a launching shell, retain identity-bound heartbeat state, enforce a deadline or recover from controller failure, emit typed terminal evidence, and reconcile a fake resource through direct and inventory views without provider mutation?

**Contract.** The proof has a $0.00 budget and a 10-second per-scenario timeout. It uses only a local fake adapter and the existing `LabDatabase` lifecycle primitives. A pass requires distinct user-service controller/watchdog control groups, a launcher that exits before the terminal artifact, content-bound controller and watchdog state, injected controller-failure and deadline scenarios, fresh heartbeat observation, duplicate-owner and mismatched-identity rejection, a terminal artifact, and both fake-provider views absent after cleanup.

**Method.** Added `durable_control_proof.py`, a project-local, reproducible proof driver. For each scenario it starts controller and watchdog as separate transient `systemd --user` services through a short-lived `systemd-run --no-block` launcher. The controller creates only a fake resource in a local JSON adapter, acquires a fenced lease, and emits state with a content hash and heartbeat. The watchdog independently persists its identity-bound heartbeat, detects stale controller state or the allocation deadline, drives `LabDatabase.sweep_due`, verifies both absence views, and emits a typed terminal record. The controller also executes negative duplicate-ownership and wrong-owner heartbeat attempts; both must raise the factory's fail-closed exceptions. The terminal validator treats an absent or incomplete terminal record as non-complete.

**Measured evidence.** [`artifacts/run-20260715T1035Z/DURABLE_PROVIDER_CONTROL_PROOF.json`](artifacts/run-20260715T1035Z/DURABLE_PROVIDER_CONTROL_PROOF.json) reports `pass: true` for both scenarios. The failure arm exited its controller with injected failure, then the separate watchdog detected the stale heartbeat and cleaned `allocation-failure`. The deadline arm kept its controller heartbeat live until its absolute deadline, then the watchdog cleaned `allocation-deadline`. In both records: the launcher returned 0 before the terminal artifact, controller and watchdog were observed in separate `/user.slice/.../app.slice/...service` control groups, direct-resource and inventory absence are true, allocation state is `cleaned`, and duplicate ownership, identity mismatch, and missing/incomplete terminal record checks were rejected. The final process audit found no `durable-control-*` user units active.

**Regression check.** `cd research/factory/tests && PYTHONPATH=../src python3 -m unittest test_labd` passed (8 tests). `py_compile` for the proof driver passed.

**Interpretation.** This is a successful generic, local lifecycle admission proof. It establishes that systemd user services can provide a durable ownership boundary outside a turn-scoped shell and can operate the existing fenced database/cleanup interface. It does not establish provider-specific deletion semantics, credentials, API reconciliation, or that any paid run is now admitted.

**Next best action.** The director may schedule exactly one provider-specific dry admission that binds this controller/watchdog interface to the selected provider adapter and verifies real direct-resource plus inventory deletion before authorizing a paid scientific allocation.
